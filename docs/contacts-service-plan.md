# Сервис «Контакты» (`contacts`)

Справочник людей общины: найти преподавателя йоги в своём городе, повара-прасадария,
ведущего киртан, аюрведа-врача, попутчика на фестиваль. Строится по
[контракту сервисного модуля](./service-module-contract.md), эталон изоляции — `union`.

Главный риск сервиса не технический, а продуктовый: справочник людей рядом с
сервисом знакомств легко превращается во «второй каталог анкет» и в обход всех
приватностных решений Union. Поэтому границы и модель видимости зафиксированы
до начала работы.

## Принятые решения

1. **Contacts — opt-in.** Карточка `ContactsProfile` создаётся явным действием
   человека, а не наследуется из портального профиля. В справочнике только те,
   кто готов к обращениям. Это закрывает большую часть приватностных рисков
   на уровне продукта, а не заплаток, и даёт лучший справочник: каталог, где
   половина «не хочет, чтобы её беспокоили», бесполезен.
2. **Отказ в Union скрывает человека в Contacts полностью, с настройкой.**
   По умолчанию отклонивший заявку исчезает из выдачи Contacts для того, кому
   отказал. В настройках карточки уровень можно ослабить до «виден, но написать
   нельзя» — для тех, кто ведёт в справочнике служение и не хочет терять охват.
   Строгий дефолт, гибкость по запросу.
3. **Таксономия «типы людей» — таблица `ContactsTag`, не enum.** Служения,
   профессии и навыки растут постоянно; каждое добавление через миграцию БД —
   тупик. Системные теги приезжают через seed, пользовательские — через модерацию.
   Духовный этап и ашрам остаются на портальных полях `User` и enum соответственно.

## Границы: Contacts vs Union

|                | Union                              | Contacts                                            |
| -------------- | ---------------------------------- | --------------------------------------------------- |
| Зачем          | партнёрство, семья                 | найти нужного человека в общине                      |
| Кто внутри     | все с профилем Union               | только явно создавшие карточку                       |
| Единица поиска | человек как личность               | человек как служение / навык                         |
| Связь          | лайк → заявка → чат                | запрос контакта → согласие → раскрытие               |
| Совместимость  | считается, показывается            | нет — это не про совместимость                       |

Из разницы следует, что Contacts **не показывает** совместимость, возраст-как-фильтр
и цели знакомства. Если эти элементы просачиваются в UI — сервис уехал в Union.

## Приватность

### Граф невидимости на уровне платформы

Ключевое требование — «отказал в знакомствах → не видит меня в контактах» — упирается
в контракт: модуль `contacts` не имеет права читать `UnionConnectionRequest`.
Значит факт «этот человек не должен меня видеть» поднимается **выше обоих сервисов**,
в платформенный `moderation` (Union уже импортирует `ModerationModule` и использует
`hiddenUserIds()` в `union-profile.service.ts`).

```prisma
enum UserHideScope { all  union  contacts }

enum UserHideSource {
  manual            // человек сам скрыл себя от конкретного
  union_declined    // отклонил заявку в Union
  union_cancelled
  moderation
}

/// Односторонняя невидимость: ownerId не показывается viewerId.
model UserHiddenFrom {
  id        String         @id @default(uuid())
  ownerId   String         // кого скрываем
  viewerId  String         // от кого скрываем
  scope     UserHideScope  @default(all)
  source    UserHideSource
  createdAt DateTime       @default(now())
  expiresAt DateTime?      // отказ может «остывать»

  @@unique([ownerId, viewerId, scope])
  @@index([viewerId, scope])
}
```

- Union при переводе заявки в `declined` вызывает
  `ModerationService.hideFrom({ owner: toUserId, viewer: fromUserId, source: 'union_declined' })`.
- Contacts вызывает `ModerationService.hiddenUserIds(userId, 'contacts')`.
- Ни один сервис не читает таблицы другого — контракт соблюдён.

**Скрытие одностороннее.** A отклонил B → A скрыт от B. Обратно не нужно: A может
передумать и сам найти B. Симметричен только жёсткий `UserBlock` — он уже такой.

**`pass` в колоде не считается отказом.** Свайп мимо — лёгкий жест, а не «не хочу
тебя видеть»; скрытие по нему разъело бы справочник за неделю. Триггер только
явный `declined`.

### Утечки, которые закрываются в коде

| Дыра                          | Решение                                                              |
| ----------------------------- | -------------------------------------------------------------------- |
| Фильтрация после выборки      | исключать в SQL (`where NOT IN`), иначе поедет пагинация              |
| Счётчики «найдено N»          | считать по **тому же** условию видимости, что и выдачу — это и есть защита |
| Прямой URL `/contacts/users/:id` | **404, не 403** — 403 подтверждает существование                   |
| Поиск по имени                | скрытый не находится по точному совпадению имени                      |
| «Был в сети»                  | огрублённо, переиспользовать `UnionActivityLevel`                     |
| Узкий фильтр как деанон       | город + пол + редкий тег = один человек; тот же порог на счётчики     |
| Корреляция с Union            | имя и аватар общие: при публикации карточки предупредить, если в Union скрыто фото/город |

**Осознанный компромисс:** человек остаётся виден в комментариях Library, в Motivation
и в Support. Полная невидимость на портале — отдельная задача, Contacts не блокирует.

**Про порог на счётчики.** В первой редакции плана он значился мерой защиты от
деанонимизации узким фильтром. При реализации выяснилось, что это не так:
карточки в выдаче видны, и посчитать их можно глазами — скрытие числа ничего
не закрывает. Настоящая защита ровно одна: **выдача, `total` и счётчики чипов
строятся по одному и тому же условию видимости**, и это условие живёт в SQL.
Порог `CONTACTS_COUNT_THRESHOLD` оставлен как удобство интерфейса («найдено
мало» вместо «найдено 2»), и относиться к нему как к защите нельзя.

### Управление собственной видимостью

```prisma
enum ContactsVisibility {
  everyone        // все участники портала
  verified_only   // только подтверждённые преданные
  same_city       // только мой город
  by_link         // не в списках, доступен по прямой ссылке
  hidden          // нигде, карточка сохранена
}
```

Дополнительно:

- **Пауза до даты** — уехал в паломничество, карточка вернётся сама.
- **Видимость по полям** (город, фото, возраст) — своим уровнем на каждое, как
  `UnionPrivacySettings`, но **независимо от Union**: в справочнике человек готов
  показать город, в знакомствах — нет.
- **Контакты не отдаются в выдаче никогда.** Телефон и мессенджеры — только через
  `ContactsRequest` → согласие → раскрытие. Email не отдаётся вообще.

## Фильтры и таксономия

Локация берётся из портального `User.homeLocation` (`city`, `country`, `lat`, `lon`
уже есть — см. `hasCompleteUnionLocation`), поэтому доступен и радиус.

Набор фильтров: **локация** (страна → регион → город → радиус) · **духовный этап**
(`seeker` / `practitioner` / `yogi` / `devotee`, отдельно «подтверждён наставником»)
· **ашрам** (брахмачари / грихастха / ванапрастха / санньяси) · **служение**
· **профессия и навык** · **языки** · **формат** (онлайн / офлайн / любой)
· **верификация** (фото, преданный) · **активность**.

«Преданный йог» — пересечение `spiritualStage` и тега служения, а не отдельная
категория справочника.

Ашрам — закрытый и стабильный набор, поэтому он остаётся enum'ом
`ContactsAshram` на самой карточке, а не тегом: тегами описывается то, что растёт.

```prisma
enum ContactsAshram  { brahmachari  grihastha  vanaprastha  sannyasi }
enum ContactsTagKind { service  profession  skill  interest }

model ContactsTag {
  id        String          @id @default(uuid())
  slug      String          @unique
  kind      ContactsTagKind
  nameRu    String
  isSystem  Boolean         @default(true)   // пользовательские — через модерацию
  sortOrder Int             @default(0)
}
```

Стартовый seed служений: пуджари, ведущий киртана, повар-прасадарий, проповедник,
книгоноша (санкиртан), наставник, организатор фестивалей, преподаватель,
переводчик. Профессии: аюрведа, астролог, юрист, врач, IT, дизайн, музыкант,
водитель.

## Дополнительные решения

1. **Анти-скрапинг.** Справочник — база живых людей. Лимиты на просмотры карточек
   и запросы контактов в сутки, логирование раскрытий, никакой выдачи контактов пачкой.
2. **«Кто смотрел мою карточку»** — таблица просмотров нужна для лимитов и заодно
   даёт полезную функцию.
3. **Журнал раскрытий с отзывом доступа** — вижу, кому открыл мессенджер, и могу закрыть.
4. **«Не показывать этого человека»** — мягкое скрытие из своей выдачи без блокировки
   (`UserHiddenFrom` с `source: manual`). Порог входа ниже, чем у блока, значит будут пользоваться.
5. **Модерация карточек с коммерческими тегами** — справочник услуг притягивает МЛМ
   и спам: статусы `draft` / `pending` / `active`.
6. **Безопасность.** Настройка «обращения только от подтверждённых преданных»
   (в Union уже есть `requestsFromVerifiedOnly`), кнопка жалобы на карточке всегда,
   памятка о встречах офлайн.
7. **Значок наставника** — `MentorVerificationRequest` уже существует; в справочнике
   это самый ценный сигнал доверия.
8. **`noindex` и доступ только авторизованным.** Каталог вайшнавов с городами
   и мессенджерами не должен попасть в поисковики.

## Модели сервиса

```prisma
// ===== Contacts service =====
model ContactsProfile      // карточка: headline, about, offers, visibility, pausedUntil, status
model ContactsTag          // таксономия справочника
model ContactsProfileTag   // связь карточки с тегом
model ContactsRequest      // запрос контакта: pending / accepted / declined   (этап D)
model ContactsDisclosure   // журнал раскрытий с возможностью отзыва           (этап D)
model ContactsView         // просмотры карточки: лимиты + «кто смотрел»       (этап E)
```

FK на `User` разрешены, на модели других сервисов — запрещены.

`ContactsProfileStatus.pending` заведён сразу, но до этапа E не используется:
премодерации ещё нет, и карточка, попавшая в `pending`, повисла бы невидимой
без пути обратно. До этапа E сервер всегда ставит `active`, а `draft`
остаётся в перечислении только под будущую премодерацию.

Карточка заводится **вместе с пользователем**: при входе
(`AuthService.ensureContactsProfile`) и при открытии своей карточки
(`ContactsService.ensureProfile`), сразу `active` / `everyone`. Справочник —
это список участников портала, а не отдельная подписка, и содержимое карточки
всё равно берётся join-ом из `User`, поэтому незаполненная запись уже
показывает человека осмысленно.

Первая редакция вела себя иначе — строку создавал только редактор, а статус
выводился из заголовка (`headline ? 'active' : 'draft'`). Это давало пустой
справочник при полностью заполненном портале и молча убирало из выдачи всякого,
кто сохранил анкету без заголовка. Способов связи автоматическая карточка не
раскрывает: телефон и мессенджеры отдаются только по действующему
`ContactsDisclosure`, а уйти из выдачи можно через `visibility: 'hidden'`.

## API

Префикс маршрутов — slug сервиса:

- `GET/PUT /contacts/profile` — своя карточка
- `GET /contacts/search` — выдача с фильтрами и счётчиками
- `GET /contacts/tags` — таксономия
- `GET /contacts/users/:id` — чужая карточка (404, если скрыт)
- `POST /contacts/requests` · `POST /contacts/requests/:id/respond`
- `GET /contacts/disclosures` · `DELETE /contacts/disclosures/:id`
- `GET /contacts/views` — кто смотрел

Frontend: `apps/web/src/app/contacts/`, компоненты в `apps/web/src/components/contacts/`,
клиент `apps/web/src/lib/contacts-api.ts`, типы `packages/shared/src/contacts.ts`.

## Этапы

- **A. Платформа — готово.** `UserHiddenFrom` с миграцией и бэкфиллом прошлых
  отказов, `ModerationService.hideFrom / unhideFrom / listHidden / hide / unhide`,
  скоуп у `hiddenUserIds` и `isHidden`, хук на `decline()` в Union, эндпоинты
  мягкого скрытия `GET union/hidden`, `POST|DELETE union/users/:id/hide`.
  Скрытие ставится **до** смены статуса заявки: упавшее скрытие оставляет
  заявку `pending` и отказ можно повторить, а обратный порядок дал бы отказ
  без защиты. Запись сервиса `contacts` заведена в seed со `status: 'coming_soon'`.
- **B. Карточка — готово.** `ContactsProfile` / `ContactsTag` / `ContactsProfileTag`
  с миграцией, 39 системных тегов сидом, модуль `apps/api/src/modules/contacts/`
  (`GET|PUT contacts/profile`, `GET contacts/tags`, `GET contacts/users/:id`),
  редактор карточки на `/contacts/profile`. Проверка `getCard` идёт в порядке
  «владелец → статус → пауза → скрытие → уровень видимости», отказ всегда 404.
  Сквозной сценарий отказа в Union прогнан на живой БД.
- **C. Поиск — готово.** `GET contacts/search` с фильтрами, гео-радиусом
  (bounding box + гаверсинус) и фасетами; страница `/contacts` с фильтрами в URL.
  Условие видимости, `total` и фасеты строятся из одного `WHERE` в SQL —
  фильтрации после выборки нет нигде. Сортировка с tiebreak по `id`, иначе
  пагинация теряет и дублирует записи. Карточка с форматом «любой» попадает
  и в выдачу «онлайн», и в «офлайн».
  Не сделано: страницы `/contacts/users/[id]`, поэтому имя в выдаче пока не ссылка.
- **D. Связь — готово.** `ContactsRequest` и `ContactsDisclosure`, шесть
  эндпоинтов, суточный лимит в `CONTACTS_REQUESTS_PER_DAY`, страницы
  `/contacts/requests` и `/contacts/disclosures`, кнопка запроса на карточке.
  Два правила, которые легко сломать «улучшением»:
  отказ **не** скрывает автоматически (в отличие от Union) — скрытие включается
  отдельной галочкой; «контакты уже открыты» означает **действующее** раскрытие,
  иначе отозванный доступ запирал бы человека навсегда.
  Сервис переведён в `active` в сиде.
- **E. Наблюдаемость.** Просмотры, «кто смотрел», модерация карточек, жалобы.

Запись сервиса в `apps/api/prisma/seed.ts` создаётся на этапе A со
`status: 'coming_soon'`, переводится в `active` после этапа D.
