# Музыка: редакционное пополнение общей аудиотеки

Дата: 2026-09-04
Статус: спека утверждена, реализация не начата
Сервис: `music` (`apps/api/src/modules/music/`)

## 1. Зачем

Каталог Музыки задуман редакционным: [план сервиса](../../music-service-plan.md)
в решении №2 и в этапе 1 говорит «наполняет редакция, а не толпа». В коде эта
часть не доделана. Сегодня трек попадает в каталог единственным путём —
личной загрузкой человека (`music/uploads`), и администратор вынужден
пользоваться тем же путём: по одному файлу, из своей квоты в 2 ГБ, с записью
на своё имя. Альбом на пятнадцать дорожек так не заводится, а перенести
готовый архив нельзя вовсе.

Спека описывает **редакционный конвейер**: администратор портала или админ
сервиса Музыка собирает партию записей из файлов, ссылок или архива, правит
метаданные таблицей и публикует их в общий каталог от имени портала.

## 2. Что уже есть и переиспользуется

Проверено по коду:

админки и три чистых модуля с тестами.

## 3. Принятые решения

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Где живёт редакционная заливка | Отдельные `MusicIngestBatch` / `MusicIngestItem` | У `MusicUpload` жёсткий `uploaderId` и завязка на личную квоту. Подмешав туда редакционное, каждый запрос про квоту, «мои загрузки» и очередь модерации обязан помнить «кроме редакционных» — однажды забудут в одном месте |
| Где живут метаданные | В `MusicTrack` со статусом `draft`, создаётся сразу после того, как файл лёг в S3 | Статус уже есть и уже отфильтрован из витрины, править умеют существующие ручки. Хранить название и исполнителя в позиции — значит описать одни поля дважды и написать второй экран правки |
| Владелец редакционного трека | `uploadedById = null` | Запись принадлежит порталу, а не тому админу, кто её завёл. Кто завёл — видно по партии |
| Источники | `upload`, `url`, `zip` — плагины первого шага, дальше общая дорога | Три выбранных источника отличаются только тем, откуда взялись байты |
| Диски (Яндекс, Google) | Не интегрируем, принимаем список прямых ссылок | Публичная ссылка на папку — это API площадки. Оба сервиса умеют отдавать прямую ссылку на скачивание; если станет мучением, добавится четвёртым плагином без правки модели и экранов |
| Видео с YouTube/VK | Не входит | Против правил площадок, тянет сторонний загрузчик и ffmpeg, а главное — портал публикует чужое исполнение под своим именем. Нужна отдельная правовая оценка |
| Личная квота | Не проверяется, вместо неё потолок партии | Редакция наполняет портал, а не свой аккаунт |
| Транскодирование | Нет, как и во всём сервисе | В v1 один файл, а не варианты качества |
| Дубль по контрольной сумме | Не ошибка, а `skipped` со ссылкой на существующий трек | При переносе архива повторы неизбежны, падать на них нельзя |

## 4. Модель данных

Отдельные модели в блоке `Music*` в конце `schema.prisma`. FK — только на
`User` и на модели своего сервиса.

```prisma
model MusicIngestBatch {
  id            String
  title         String                  // «Аванти — Гопинатх, 2019»
  createdById   String?                 // админ, SetNull при удалении аккаунта
  status        MusicIngestBatchStatus  // draft | running | ready | published | failed
  rightsBasis   MusicUploadRightsBasis  // основание прав редакции
  rightsNote    String?                 // откуда взяли, словами
  artistId      String?                 // значения по умолчанию для позиций
  albumId       String?
  categoryIds   String[]
  language      String?
  isLiveRecording Boolean @default(false)
  createdAt     DateTime
  updatedAt     DateTime
}

model MusicIngestItem {
  id            String
  batchId       String                  // Cascade
  source        MusicIngestSource       // upload | url | zip
  sourceRef     String                  // адрес, имя файла в архиве или имя выбранного файла
  position      Int
  status        MusicIngestItemStatus   // waiting | fetching | stored | skipped | failed
  storageKey    String?
  checksum      String?
  trackId       String?                 // созданный черновик, SetNull
  failureReason String?
  attempts      Int @default(0)
  createdAt     DateTime
  updatedAt     DateTime

  @@index([status, updatedAt])
  @@index([batchId, position])
}
```

Ключ объекта — `music/portal/<batchId>/<uuid>.<ext>`, рядом с личным
`music/uploads/<userId>/…`: по префиксу видно, чьё это, и уборка партии
удаляет ровно свой префикс.

## 5. Конвейер

Одна дорога, различие только в первом шаге.

1. **Приём.** `upload` — браузер льёт подписанным PUT прямо в S3, по три
   файла разом. `url` — сервер качает потоком. `zip` — сервер распаковывает
   архив по одному файлу.
2. **Проверка.** `music-upload-validate.ts`: mime `audio/mpeg` и `audio/mp4`,
   до 150 МБ, до 4 часов, до 320 kbps, дубль по контрольной сумме. Личная
   квота не проверяется; проверяется потолок партии.

   Контрольная сумма берётся по-разному, и это важно. У `upload` — ETag
   объекта, как сейчас: для загрузки одним PUT это MD5 содержимого, и он
   достаётся бесплатно из `HEAD`. У `url` и `zip` байты и так проходят через
   наш процесс, поэтому сумма считается на лету при потоковой записи. ETag
   для них не годится: у multipart-загрузки это не MD5 содержимого, и дубли
   по нему не ловятся.
3. **Разбор.** `music-metadata-reader.ts` читает теги, длительность, битрейт
   и встроенную обложку. Название, исполнитель и альбом из тегов — это
   предположение, которое админ правит.
4. **Черновик.** Создаётся `MusicTrack` в `draft` с настройками партии по
   умолчанию. Позиция переходит в `stored` и хранит `trackId`.
5. **Публикация.** Админ проверяет таблицу и публикует: черновики переходят в
   `published` с `publishedAt`, партия — в `published`.

**Где крутится.** Стадия в `music-worker.service.ts`. Его тик в 10 минут для
этой работы не годится — админ смотрит на экран и ждёт, — поэтому у приёма
свой тик 15 с: сначала дешёвый `count` по индексу `(status, updatedAt)`, при
пустой очереди сразу выход. Запуск партии дёргает стадию сразу, не дожидаясь
тика. Одновременно обрабатываются две-три позиции: канал не резиновый.

**Устойчивость.** Клейм позиции — `updateMany` с проверкой статуса, как в
остальном воркере. Три попытки (`attempts`), затем `failed` с причиной
словами. Позиция, застрявшая в `fetching` дольше получаса, возвращается в
`waiting` по `updatedAt`.

## 6. Источники и ограничения

**`upload`.** Тот же подписанный PUT, что у людей, ключ — в редакционном
пространстве. Оборванная заливка оставляет позицию в `waiting`, её
перезаливают, не трогая остальные.

**`url`.** Скачивает сервер, и без трёх защит этого делать нельзя:

- **Внутренняя сеть.** API стоит рядом с Postgres, Redis и панелью
  развёртывания. Схема только `http`/`https`; адрес резолвится и сверяется с
  приватными диапазонами (`127/8`, `10/8`, `172.16/12`, `192.168/16`,
  `169.254/16`, `::1`, `fc00::/7`), **и проверяется заново на каждом
  редиректе** — иначе внешний сайт одним `302` уводит нас внутрь. Редиректов
  не больше трёх.
- **Размер.** `Content-Length` — заявление сервера, а не факт. Поток
  обрывается по фактически прочитанным байтам при превышении предела.
- **Память.** Файл идёт в S3 потоком через multipart. Три параллельных
  скачивания по 150 МБ в буфере — почти полгигабайта RSS, и API ляжет.

**`zip`.** Распаковка потоком, по одному файлу. Не больше 200 записей и не
больше 4 ГБ в распакованном виде на партию — иначе архив на 40 КБ
разворачивается в гигабайты. Пути с `..` и абсолютные отбрасываются; берутся
только `.mp3` и `.m4a`; вложенные архивы игнорируются. Порядок дорожек —
номер из тегов, а при его отсутствии натуральная сортировка по имени файла,
чтобы `10` шло после `9`.

## 7. API

Контроллер `music/admin/ingest`, префикс — слаг сервиса, как у остальных
админ-ручек Музыки. Все под `AuthGuard` и проверкой `isAdmin`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `music/admin/ingest` | список партий: объём, число позиций, статус |
| POST | `music/admin/ingest` | создать партию |
| GET | `music/admin/ingest/:id` | партия с позициями и их треками |
| PATCH | `music/admin/ingest/:id` | настройки по умолчанию |
| DELETE | `music/admin/ingest/:id` | удалить партию, её файлы и черновики |
| POST | `music/admin/ingest/:id/files` | подписанные PUT на N файлов, создаёт позиции |
| POST | `music/admin/ingest/:id/files/:itemId/complete` | браузер сообщил, что залил |
| POST | `music/admin/ingest/:id/urls` | добавить позиции списком адресов |
| POST | `music/admin/ingest/:id/archive` | добавить архив (файлом или ссылкой) |
| POST | `music/admin/ingest/:id/start` | запустить обработку |
| POST | `music/admin/ingest/:id/retry` | повторить упавшие |

Правка метаданных идёт существующим `PATCH music/admin/catalog/tracks/:id` —
нового API для этого не заводим.

## 8. Админка

Пятая вкладка **«Пополнение»** в `admin-tabs.tsx`, рядом с очередью,
жалобами, справочниками и подборками. В `ADMIN_NAV` править нечего: раздел
`/admin/music` там уже есть со скоупом `music`, и админ сервиса получает
доступ сам собой.

**Список партий** (`/admin/music/ingest`): название, кто и когда завёл, число
позиций, суммарный объём, статус. Объём стоит рядом со статусом намеренно —
это единственное место, где видно, во что обходится каталог.

**Страница партии** (`/admin/music/ingest/[id]`) — три блока:

1. *Шапка:* что применить ко всему — исполнитель, альбом, категории, язык,
   «запись с программы», основание прав и строка «откуда взяли». Последнее не
   бюрократия: когда придёт претензия, отвечать придётся по конкретной
   записи.
2. *Добавление:* вкладки «Файлы», «Ссылки» (по адресу на строку), «Архив».
3. *Таблица позиций:* статус и прогресс у каждой, правка метаданных прямо в
   строке, отметка нескольких строк и применение к ним исполнителя или
   альбома одним движением.

Кнопки: «Запустить», «Повторить упавшие», «Опубликовать всё», «Удалить
партию». Дубль показывается строкой «уже есть в каталоге» со ссылкой на
существующий трек.

**«Опубликовать и собрать подборку»** — партия одним движением превращается в
системный плейлист. Механизм системных подборок уже написан и показывается на
витрине; пустует он потому, что в каталоге нечего собирать.

## 9. Ошибки и деньги

Партия не падает целиком: одна недоступная ссылка не отменяет сорок
скачавшихся. У позиции причина текстом («сервер ответил 403», «не аудио:
`text/html`», «длиннее четырёх часов», «уже есть в каталоге»), «Повторить
упавшие» берёт только их. Механизм, требующий идеального входа, не доживёт до
второй партии: в перенесённом архиве часть ссылок протухла всегда.

Потолок партии — `MUSIC_INGEST_BATCH_QUOTA_BYTES`, по умолчанию 20 ГБ. У
файлов и у ссылок с честным `Content-Length` он проверяется до скачивания, а
у остальных — по фактически принятым байтам: позиция обрывается, а партия
перестаёт брать новые. Иначе потолок обходится сервером, который про свой
размер промолчал. Занятый редакцией объём показывается в шапке
админки рядом с личными загрузками: сейчас там учитываются только люди, и
портальные записи прошли бы мимо счёта. Час киртана в 320 kbps — около
140 МБ; тысяча записей это 100–140 ГБ плюс трафик на каждое прослушивание, и
цифра должна быть перед глазами того, кто нажимает «Опубликовать всё», а не
всплывать в счёте за месяц.

## 10. Тесты

Чистая логика выносится и покрывается, обёртки — нет:

- `ingest-url-guard.ts` — схема, приватные диапазоны, литеральные IP,
  редирект во внутреннюю сеть, предел редиректов. Это код, закрывающий дыру,
  и покрывается первым;
- `ingest-zip-entry.ts` — какие записи архива берём: расширение, `..` в пути,
  абсолютный путь, вложенный архив, пределы по числу и объёму;
- `ingest-order.ts` — номер из тегов важнее имени файла, натуральная
  сортировка (`track2` перед `track10`);
- `ingest-state.ts` — переходы позиции, агрегированный статус партии, что
  считается зависшим по `updatedAt`;
- расширение `music-upload-validate.spec.ts` — редакционная ветка: без личной
  квоты, но с потолком партии.

Воркер и загрузчик тестами не покрываются — как воркер Мотивации, чья логика
вынесена в `story-image.ts`.

## 11. Этапы

| # | Шаг | Содержание |
| --- | --- | --- |
| 1 | Модель | две модели и энумы, миграция, типы в `packages/shared/src/music.ts` |
| 2 | Партия и `upload` | ручки партии, подписанный PUT в редакционное пространство, черновой трек, стадия воркера с быстрым тиком |
| 3 | Админка | вкладка «Пополнение», список партий, страница партии с таблицей и массовой правкой |
| 4 | `url` | загрузчик потоком, `ingest-url-guard`, ретраи, подъём зависших |
| 5 | `zip` | распаковка потоком, `ingest-zip-entry`, порядок дорожек |
| 6 | Витрина | «Опубликовать и собрать подборку», строка объёма редакции в шапке админки |

Первый ощутимый результат — после шага 3: админ заливает альбом пачкой и
публикует. Шаги 4–5 добавляют источники, ничего не переписывая.

## 12. Что намеренно не входит

Транскодирование и варианты качества; интеграции с API Яндекс.Диска и Google
Drive; вытяжка звука с YouTube и VK; приём заявок от храмов и исполнителей
(отдельный сценарий, в этой работе не нужен); автоматическое распознавание
исполнителя по звуку; правка текстов бхаджанов в конвейере — она уже есть в
карточке трека.
