# ИИ-астрология VedaMatch: ведическая карта в бесплатной бете

Статус: план, к реализации.
Сервис: `astro` (рабочее название «Джйотиш»).

## 1. Цель

Дать пользователям VedaMatch ведическую натальную карту с ИИ-разбором и ежедневную
панель транзитов, бесплатно на время беты, не открыв при этом неконтролируемый расход
на LLM.

Классическая (западная) астрология в объём беты **не входит**, но слой расчёта
проектируется так, чтобы она включалась конфигурацией (тропический зодиак + Плацидус +
аспекты), а не переписыванием — см. §4.

### Принятые решения

| Развилка | Решение |
|---|---|
| Движок эфемерид | pure-JS под MIT; Swiss Ephemeris не берём из-за AGPL-3.0 |
| Объём MVP | ведическая натальная карта + ежедневные транзиты с пушами |
| Контроль расходов | дневная квота на пользователя + глобальный бюджет с kill-switch + вечный кэш интерпретаций, всё настраивается в админке |
| Доступ | всем авторизованным (не по приглашениям) |

## 2. Главный архитектурный принцип

**Расчёт и интерпретация — разные слои, и они не смешиваются.**

ИИ никогда не вычисляет положения планет. LLM галлюцинирует градусы, накшатры и даши,
и это ловится пользователями мгновенно — для астрологического сервиса это фатально
репутационно. Схема строго такая:

```
birth data → [детерминированный расчёт] → chart JSON → [LLM интерпретирует JSON] → текст
```

Из этого следуют два практических вывода:

- Расчёт детерминирован → кэшируется вечно по хэшу входа. Открытие карты повторно
  бесплатно.
- Весь денежный риск беты сосредоточен ровно в одном месте — генерации текста. Значит
  и контролировать надо одно место.

## 4. Слой эфемерид

### 4.1 Интерфейс

Реализация прячется за интерфейсом, чтобы замена движка (в т.ч. на лицензированный
Swiss Ephemeris в будущем) не расползалась по коду:

```ts
// modules/astro/ephemeris/ephemeris-provider.ts
export interface EphemerisProvider {
  readonly version: string; // входит в fingerprint карты
  positions(at: Date): BodyPosition[]; // 9 грах: долгота, широта, скорость (ретро = speed < 0)
  angles(at: Date, latitude: number, longitude: number): ChartAngles; // лагна, MC, наклон, LST
}
```

Провайдер отдаёт **тропические** видимые координаты на дату и ничего не знает ни об
аянамше, ни о накшатрах. Шов проходит именно здесь: ведический слой применяет аянамшу
поверх, а западная карта переиспользует тот же провайдер без единой правки.

`version` обязателен: он входит в fingerprint карты, иначе после смены движка в кэше
останутся карты, посчитанные старой математикой.

### 4.2 Выбранный движок (Э0 закрыт)

**`astronomia` 4.2.0, лицензия MIT.** Реализация:
`apps/api/src/modules/astro/ephemeris/astronomia-provider.ts`.

Рассматривался также `circular-natal-horoscope-js` (Unlicense) как готовый каркас
карты, но он не понадобился: `astronomia` даёт серии VSOP87 для планет и ELP для Луны,
а асцендент — замкнутая тригонометрическая формула в десяток строк. Вторая зависимость
не окупалась.

Swiss Ephemeris не нужен: по точности отрыва нет (см. 4.3), а AGPL-3.0 и нативная
сборка в Docker — реальные издержки, которые нечем оправдать.

Ведическая надстройка пишется нами в любом случае и является простой арифметикой поверх
долгот: 27 накшатр с падами, вимшоттари-даша, варга D9 (навамша), комбустия. Раху/Кету
как средние узлы уже отдаёт провайдер.

### 4.3 Результат валидации (гейт Э0 пройден)

Тесты: `apps/api/src/modules/astro/ephemeris/astronomia-provider.spec.ts`, 43 кейса.

**Позиции планет — против JPL Horizons (NASA), величина 31, эпохи 1879/1950/2000/2026.**
Внешняя истина, а не собственный вывод библиотеки: тест, зафиксировавший свой же
результат, доказывает неизменность, но не правильность.

| | худшее расхождение |
|---|---|
| Солнце | 0.13″ |
| Луна | 4.56″ |
| Меркурий…Сатурн | 0.25″ |

При паде в 3°20′ (12000″) запас превышает тысячу крат. Для баланса первой махадаши
4.56″ по Луне дают сдвиг около 8 часов на цикле в 120 лет.

**Асцендент — сверка замкнутой формулы с независимым численным поиском точки восхода.**
Совпадение до 0.0000″ на шести случаях: Москва, Мумбаи, Ульм 1879, Кито (экватор),
Рейкьявик (64° с.ш.), Сидней (южное полушарие). Внешний эталон здесь не нужен — две
независимые математики либо сходятся, либо нет.

Две ошибки, найденные валидацией и достойные упоминания, потому что обе тихие:

1. **Двойной учёт нутации.** `elliptic.position` уже возвращает видимые координаты,
   и прибавление Δψ поверх давало всем пяти планетам одинаковый сдвиг ±17″ с периодом
   18.6 года. На одной тестовой дате это выглядит как постоянная погрешность движка.
   Поймано только потому, что эпох было четыре, а смещение у всех планет совпадало
   до сотых.
2. **Ветвь пересечения горизонта.** Асцендент — куспид первого дома, а дома 1–6 лежат
   под горизонтом: высота пересекает ноль сверху вниз. Восходящее пересечение — это
   десцендент, ровно 180° мимо.

**Аянамша Лахири — закрыта частично, см. §6.**

## 5. Данные

### 5.1 Модели Prisma

Источник истины — `apps/api/prisma/schema.prisma`, блок `// ===== Astro service =====`.
Дублировать его здесь смысла нет: копия разойдётся со схемой. Что реализовано:

| Модель | Роль |
|---|---|
| `AstroBirthData` | данные рождения: момент UTC, локальные дата и время, место, зона |
| `AstroReading` | текст раздела; ключ кэша — отпечаток карты + раздел + язык + версия промпта |
| `AstroUsage` | расход пользователя за сутки |
| `AstroBudgetDay` | расход всего сервиса за сутки и отметка аварийной остановки |
| `AstroSettings` | единственная строка лимитов, правится из админки |

Энумы: `AstroTimeAccuracy`, `AstroSection`. Все имена с префиксом `Astro`, FK только
на `User`.

**Отличие от первоначального плана: таблицы `AstroChart` нет.** Расчёт детерминирован
и дёшев, а отпечаток уже содержит версию движка, поэтому карты не хранятся, а разборы
ключуются отпечатком напрямую. Одна таблица и один слой синхронизации меньше.

Миграции: `20260809160000_astro_birth_data`, `20260809170000_astro_readings_quotas`.
Обе написаны сверкой схемы из git с текущей (`prisma migrate diff`), а не применением
к базе: история миграций проекта содержит запись, изменённую после применения, и
`migrate dev` из-за неё требует сброса базы.

### 5.2 Геокодинг и таймзоны (Э1 закрыт)

Самая частая причина неверных карт — не математика, а час смещения.

**Отклонение от исходного плана: своего датасета GeoNames нет.** В портале уже был
`GET /geo/search` ([geo.controller.ts](../../../apps/api/src/modules/users/geo.controller.ts),
Nominatim с фолбэком на Photon), которым пользуется профиль. Онбординг астрологии
переиспользует его же с фронта; астро-бэкенд геокодингом не занимается вовсе. Сидить
25 тыс. населённых пунктов ради второго поиска по городам не было смысла.

Точность места, к слову, почти не важна: 1° долготы — это 4 минуты времени, соседний
город в полусотне километров сдвигает лагну на считаные минуты дуги.

- Часовой пояс по координатам — `tz-lookup` (CC0, офлайн, синхронный), отдаётся
  отдельным `GET /astro/birth-data/timezone` **до сохранения**: человек должен увидеть
  и подтвердить пояс, а не обнаружить его в готовой карте. Для приграничных мест есть
  ручное переопределение.
- `bornAtUtc` считается через `luxon` с исторической tzdata. Проверено тестами:
  Москва в мае 1987-го — UTC+4 (декретное плюс летнее), в январе 2016-го — UTC+3;
  Ульм в 1879-м — UTC+0:53, местное среднее солнечное время, поясов в Германии тогда
  ещё не ввели; Мумбаи — UTC+5:30.
- **Несуществующее локальное время** в час перевода стрелок Luxon считает валидным и
  молча сдвигает на час. Отдельный признак `nonexistentLocalTime` ловит это обратным
  прогоном стенных часов, и интерфейс предупреждает. Жёсткой ошибки нет: в документах
  действительно может стоять час из «пропавшего» интервала.
- `timeAccuracy = unknown` → карта считается на 12:00 местного, дома и лагна
  **скрываются**, разбор ограничивается тем, что от времени не зависит. Показывать
  асцендент по выдуманному времени нельзя.

### 5.3 Изоляция

Модуль `astro` импортирует только `AuthModule`, `PrismaService`, типы `@vedamatch/shared`
и `EventEmitter2`. `BillingService` **не импортируется**: в бете доступ определяется
`AstroSettings.enabled` и квотами, а видимость сервиса — записью `Service` в каталоге,
которой заведует портал. Когда режим вернётся в `business`, платный гейт добавляется
отдельным решением, а не связкой модулей сейчас.

## 6. Ведический слой (Э2 закрыт)

`apps/api/src/modules/astro/vedic/`, 96 тестов.

### 6.1 Аянамша

Считается по определению, давшему ей имя: «читра пакша» — «со стороны Читры», то есть
сидерический круг закреплён так, чтобы Спика стояла ровно на 180°. Астрометрия Спики
берётся из **SIMBAD** (`* alf Vir`, ICRS J2000) — внешний источник, не константа по
памяти; собственное движение учитывается.

| эпоха | значение |
|---|---|
| 1956.0 | 23°13′51″ |
| 2000.0 | 23°50′10″ |
| 2026.0 | 24°12′16″ |

Прирост 50.3″ в год совпадает с общей прецессией — независимая физическая проверка,
которая ловит ошибку в эпохе или единицах собственного движения.

**Что остаётся открытым.** Официальная константа Индийского комитета календарной
реформы и буквальное «Спика на 180°» расходятся примерно на **1 угловую минуту**:
комитет зафиксировал круглое значение на эпоху, а не положение звезды. Разные
программы дают разный Лахири в этих же пределах. Одна минута не двигает ни знак (30°),
ни накшатру (13°20′), ни паду (3°20′) — кроме планет, стоящих в пределах минуты от
границы. Перед выходом из беты значение стоит сверить с астрологом или опубликованной
таблицей; тест намеренно проверяет широкий диапазон, чтобы не закрепить одну
реализацию как истину.

### 6.2 Что считается

Раши, бхавы по целым знакам от лагны, 27 накшатр с падами, варга D9, вимшоттари-даша
с махадашами и антардашами, ретроградность, астангата (сожжение).

Даши: 120-летний цикл, первый период урезан пройденной долей накшатры Луны. Длина года
вынесена в именованную константу `DASHA_YEAR_DAYS` — традиция знает и савана-год в 360
суток, и выбор смещает границы периодов на дни.

Навамша считается прямым счётом 108 делений по кругу. Это тождественно правилу стихий
(огонь начинает с Меши, земля с Макары, воздух с Тулы, вода с Карки), потому что 108
кратно 12; тесты проверяют совпадение на всех четырёх стихиях.

### 6.3 Найденная ошибка точности

Тесты границ поймали настоящий баг, а не только сами себя.

`((x % 360) + 360) % 360` — идиоматичное приведение угла — **портит уже корректные
значения**: для малого x оно прибавляет 360 и вычитает обратно, теряя младшие биты.
Вместе с делением на непредставимую константу (`360/27`, `30/9`) этого хватало, чтобы
`floor` срывался на единицу вниз ровно на границах делений. `navamsaRashiOf(10)`
возвращал третью навамшу вместо четвёртой, а границы навамш приходятся на круглые 10°
и 20° внутри знака — попадание туда совершенно обычное.

Исправлено двумя приёмами: короткое замыкание в `normalize360` для значений, уже
лежащих в диапазоне, и умножение до деления (`floor(lon * 108 / 360)` вместо
`floor(lon / (360/108))`). Регрессионные тесты закреплены.

Отдельно: границы накшатр в двоичной дроби непредставимы в принципе, поэтому тест
проверяет не попадание в границу, а корректный переход через неё.

### 6.4 Отпечаток карты

`sha256(версия движка | момент UTC | широта | долгота | точность времени | аянамша |
система домов)`. Версия движка входит обязательно: иначе после смены эфемерид в кэше
остались бы карты, посчитанные другой математикой, и отличить их было бы нечем. Момент
просмотра в отпечаток НЕ входит — он меняет текущую дашу, но не саму карту.

`GET /astro/chart` намеренно без квоты: расчёт детерминирован и дёшев, платить надо за
интерпретацию. Карта должна открываться и при выключенном ИИ.

## 7. API

Все маршруты с префиксом слага сервиса. Галочкой отмечено реализованное.
Место рождения ищется портальным `/geo/search`, своего поиска у сервиса нет (§5.2).

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/astro/birth-data` | текущие данные рождения и прогресс ✅ |
| PUT | `/astro/birth-data` | сохранить/изменить ✅ |
| GET | `/astro/birth-data/timezone` | пояс по координатам, до сохранения ✅ |
| GET | `/astro/chart` | расчёт карты, без ИИ, без квоты ✅ |
| GET | `/astro/readings` | все разделы: тексты из кэша и причины блокировок ✅ |
| POST | `/astro/readings/:section` | сгенерировать раздел (тратит квоту) ✅ |
| GET | `/astro/quota` | остаток квоты и статус ИИ ✅ |
| GET | `/astro/today` | транзиты и текущая даша на сегодня |
| GET | `/admin/astro/settings` | лимиты (только роль admin) ✅ |
| PATCH | `/admin/astro/settings` | изменить лимиты ✅ |
| GET | `/admin/astro/usage?days=` | расход за N дней, топ потребителей ✅ |
| POST | `/admin/astro/resume` | снять аварийную остановку ✅ |

`GET /astro/chart` намеренно бесквотный: математика дешёвая, и пользователь должен
видеть карту, даже когда ИИ выключен kill-switch'ем.

## 8. ИИ-слой

`AstroGenerationService` по образцу `MotivationGenerationService`, переменные окружения
`ASTRO_AI_API_KEY`, `ASTRO_AI_BASE_URL`, `ASTRO_TEXT_MODEL`.

### Промпт

Системная часть фиксирует границы:

- В контекст подаётся **готовый chart JSON**. Модели прямо запрещено пересчитывать,
  уточнять или изменять любые градусы, знаки, накшатры и даты даш — только
  интерпретировать переданное.
- Никаких предсказаний смерти, болезней, судебных исходов; никаких медицинских,
  финансовых и юридических рекомендаций.
- Тон вайшнавский, уважительный, несектантский (как в `motivation`); акцент на свободе
  воли и практике, а не на фатализме.
- Ответ строго JSON, `response_format: { type: 'json_object' }`.

`promptVersion` — константа в коде, входящая в уникальный ключ `AstroReading`. Правка
промпта автоматически инвалидирует кэш, ручных миграций не требуется.

### Разделы

`overview`, `lagna`, `moon_nakshatra`, `career`, `relationships`, `strengths`,
`dasha_current`, `practice`. Генерируются лениво, по одному, по раскрытию аккордеона —
пользователь, посмотревший только обзор, не оплачивает остальные семь.

### Реализация (Э4 закрыт)

`astro-generation.service.ts` (провайдер), `astro-reading.service.ts` (кэш, порядок
проверок), `astro-quota.service.ts` (учёт и бюджет), `astro-settings.service.ts`.

`ASTRO_PROMPT_VERSION` входит в ключ кэша. **Любая правка промпта обязана поднимать
версию**: иначе пользователи увидят тексты, собранные по старым правилам, и по
содержимому это не отличить.

Таблицы `AstroChart` из плана нет и не понадобилось: расчёт детерминирован и дёшев,
а отпечаток уже содержит версию движка, поэтому разборы ключуются прямо им. Побочное
следствие — у людей с совпадающими данными рождения кэш общий; по существу это верно,
текст описывает карту, а не личность.

Порядок проверок в `generate` важен и именно такой: **кэш → доступность раздела →
бюджет и квота → провайдер**. Каждый следующий шаг дороже предыдущего, самый дорогой —
последний. Готовый раздел отдаётся из кэша, даже когда квота исчерпана: он ничего не
стоит, а ограничивать надо появление новых текстов.

Расход списывается ПОСЛЕ ответа провайдера и по фактическому `usage`, а не по
запрошенному. Если провайдер упал, ни запись разбора, ни списание не происходят.

## 9. Контроль расходов

Четыре рубежа, от дешёвого к дорогому:

1. **Вечный кэш.** `AstroReading` уникален по `(chartId, section, locale, promptVersion)`.
   Повторный просмотр стоит ноль. Регенерация — только явной кнопкой и списывает квоту.
2. **Дневная квота пользователя.** `AstroUsage` по `(userId, day)`: не более
   `dailyReadingsPerUser` генераций и `dailyTokensPerUser` токенов в сутки. Проверка
   до вызова провайдера, инкремент — после, по фактическому `usage` из ответа. Сброс
   естественный, сменой ключа `day`.
3. **Глобальный дневной бюджет и kill-switch.** `AstroBudgetDay` копит расход по всему
   сервису. При превышении `dailyTokenBudget` или `dailyCostLimitUsdCents`
   проставляется `haltedAt`, и сервис переходит в режим «только расчёт»: карта, дома,
   даши и транзитные факты показываются, ИИ-тексты — из кэша либо заглушка. Сервис не
   ломается, он деградирует.
4. **Общие транзитные фразы.** Текст «Луна проходит вашу 7-ю бхаву» зависит от пары
   (планета, дом, знак), а не от личности. `AstroTransitPhrase` кэширует его один раз
   на весь портал. Это превращает ежедневную рассылку из линейной по числу
   пользователей в практически постоянную по стоимости — иначе именно она съела бы
   бюджет беты.

### Админка (Э5 закрыт)

Страница `apps/web/src/app/admin/astro/`, ссылка в меню администратора рядом с
«Настройками». Роль проверяется и на странице, и в каждом методе контроллера:
`AuthGuard` подтверждает вход, но не права — так же устроен `AdminBillingModeController`.

Что на странице: расход за сегодня против лимита, три переключателя (сервис, генерация,
пуши), четыре числовых лимита, расход по дням полосами и топ-20 потребителей с именами.
График — обычные полосы на CSS: масштаб виден, зависимостей ноль. День с аварийной
остановкой красится отдельным цветом.

Правки лимитов проверяются на сервере по границам (`astro-admin.service.ts`). Границы
нужны не от злого умысла, а **от опечатки**: лишний ноль в дневном бюджете стоит
реальных денег, и заметить его постфактум трудно. Ноль при этом разрешён — это
осмысленное «запретить полностью».

Кнопка снятия остановки появляется только когда остановка есть, и рядом сказано, что
именно продолжает работать. Повторно остановка встанет сама, если расход по-прежнему
за лимитом: `isHalted` проверяет и отметку, и фактическое превышение.

## 10. Дневные транзиты и пуши (Э6 закрыт)

Реализация: `apps/api/src/modules/astro/transits/`.

### 10.1 Единственный по-настоящему дневной сигнал

Из девяти грах транзитная Луна — единственная, что проходит бхаву целиком за
~2.25 суток; остальные восемь стоят в доме неделями и месяцами и для ежедневной
рассылки не несут новой информации по сравнению со вчерашней. Поэтому дайджест
считает только её: `computeTransitFacts()` — чистая функция, бхава транзитной
Луны относительно НАТАЛЬНОЙ лагны.

Проверка не выдумана заново: транзитная Луна в момент самого рождения обязана
совпасть с натальной Луной уже построенной карты — тест сверяет ровно это,
а не повторяет вручную выведенные числа.

### 10.2 Экономика держится на одной детали

Ключ общей фразы — `moon|bhava:N`, только номер дома. Он не содержит ни знака,
ни накшатры, ни человека, поэтому в промпт модели уходит только число: она не
может узнать о пользователе больше, чем уже видно из бхавы. Ровно поэтому фразу
можно шарить — вариантов не больше 12 в сутки независимо от размера базы,
именно то экономическое обещание, ради которого §9 вводил кэш общих фраз.

Расход на неё не персональный: `AstroQuotaService.recordSystemUsage()` пишет
только в общий дневной бюджет, не в `AstroUsage` — иначе первый человек, чья
бхава совпала с ещё не сгенерированной фразой, выглядел бы в админке так, будто
потратил чужую квоту.

### 10.3 Изоляция сохранена через события, не прямой импорт

`astro` не импортирует `NotificationsModule`: воркер публикует самодостаточное
событие `astro.transit.digest-ready` (recipientId + готовая фраза) через
`EventEmitter2`, `NotificationsListener` сам решает, слать ли пуш, по
`NotificationPreference.transits` — новой категории, добавленной по тому же
шаблону, что `chat`/`connections`/`support`. Публикатор не переписывает и не
дублирует логику подписчика — тот же принцип, что уже описан в
`docs/service-module-contract.md`.

### 10.4 Джоб — тот же паттерн, что уже есть в проекте

`AstroTransitWorkerService` устроен как `MotivationWorkerService`: опрос по
таймеру вместо `@nestjs/schedule` (не тянуть библиотеку ради одного джоба),
необязательный Redis-лок, который просто отсутствует в разработке, и
идемпотентность на календарные сутки.

> Уточнено после беты. Идемпотентность в памяти процесса не пережила первый же
> деплой: рестарт обнулял `lastRunDate`, и пуш уходил заново, вне расписания.
> Теперь рассылка ограничена окном 09:00–11:00 МСК, а признак «отправлено»
> живёт в `AstroTransitDigest.pushedAt`: строка получателя занимается
> атомарным `updateMany(pushedAt: null)` до публикации события, поэтому ни
> рестарт, ни второй инстанс не повторяют пуш. Поле `lastRunDate` осталось
> только как дешёвая отсечка лишних сканов внутри одного процесса.

Отбор получателей: известное время рождения (без него бхавы не бывает) и
активность за 14 дней — свежие данные рождения или использование разборов.
Ошибка на одном человеке не останавливает рассылку остальным — тот же принцип,
что в `NotificationsListener.deliver`.

Дайджест пишется в БД всегда, даже без фразы (ИИ мог быть выключен) — карта
никогда не выглядит как пустое место, только как «разбор появится позже».
`GET /astro/today` использует тот же сервис, что и джоб: пользователь, зашедший
раньше рассылки, получает те же факты и тот же кэш фразы, что получит вечером
в пуше.

## 11. Frontend (Э3 закрыт)

Структура по контракту сервиса:

- `apps/web/src/app/astro/` — онбординг данных рождения (`/astro`) и карта
  (`/astro/chart`).
- `apps/web/src/components/astro/` — локальные компоненты.
- `apps/web/src/lib/astro-api.ts` — клиент поверх общих fetch-хелперов.

**Карта — южноиндийский стиль на чистом SVG, без библиотек.** Сетка 4×4, знаки
закреплены за клетками и никогда не двигаются: в этом весь смысл стиля — привыкший
человек находит знак, не читая подписей. Двигаются только грахи. Северноиндийский ромб
устроен наоборот (закреплены дома) и в бету не входит.

`viewBox` фиксирован, размер задаётся снаружи через CSS; цвета берутся из
`currentColor`, поэтому тема переключается без второго набора стилей.

Лагна метится диагональю в углу своей клетки — так её отмечают в традиции. При
неизвестном времени рождения диагонали нет и номера бхав не выводятся вовсе: выдуманные
дома хуже отсутствующих.

Таблица положений даёт градусы с минутами, а не округления — именно по ней карту
сверяют с другой программой, и расхождение в четверть градуса должно быть видно.

**Названия раши и накшатр живут в `packages/shared`**, а не в сервисе: их читают и
расчёт, и интерфейс, а 27 накшатр, продублированных в двух местах, разойдутся при первой
же правке. Прецедент в пакете уже был — `VEDABASE_BOOK_SLUGS`.

Разделы ИИ-разбора (Э4) — аккордеон с ленивой генерацией и явным индикатором остатка
квоты. Когда сработал kill-switch, интерфейс честно показывает «разборы временно
недоступны, карта считается», а не крутит спиннер.

## 15. Совместимость карт (гуна-милан, Э7)

Добавлена по запросу поверх исходного плана. Реализация: `apps/api/src/modules/astro/compatibility/`.

### 16.1 Согласие — отдельный процесс внутри astro

Запрос на сопоставление и ответ на него не зависят от статуса анкет в Union:
инициатором может быть любой пользователь портала. Карта целиком (время, место
рождения) второй стороне никогда не передаётся — до принятия запроса получатель
видит только имя и аватар инициатора (то же, что уже видно в Union), не знак и не
накшатру его Луны. `score` в DTO запроса — `null`, пока `status !== 'accepted'`;
это проверено тестом отдельно, как инвариант приватности, а не побочный эффект.

Встречный запрос (Б уже написал А, когда А пишет Б) автоматически трактуется как
взаимное согласие, а не создаёт второй параллельный pending — иначе у одной пары
могло бы одновременно существовать два независимых запроса с разным исходом.

### 16.2 Гуна-милан: что уверенно, а что упрощено

Расчёт — чистая функция по Луне обоих людей (`guna-milan.ts`), восемь критериев,
максимум 36 очков по традиции. В отличие от эфемерид, для гуна-милана нет внешнего
эталона вроде JPL — это свод правил традиции, а не физика, и источники расходятся.
Разделение по уверенности:

**Уверенно** (стандартные таблицы джйотиша, используются далеко за пределами
гуна-милана): планетарная дружба Парашары, деление 27 накшатр на надьи и ганы,
владыки знаков, арифметика счёта тары и позиции бхакута.

**Сознательно переосмыслено:** прежняя варна-кута (1 очко за иерархию
брахман>кшатрий>вайшья>шудра) заменена на группировку по темпераменту — те же 4
группы по стихии знака, тот же балл, без иерархии в коде. Платформа несектантская,
и воспроизводить кастовое ранжирование в алгоритме знакомств означало бы протащить
его в продукт незаметно для пользователя.

**Упрощено с явной пометкой** (`GUNA_MILAN_VERIFICATION_NOTE` в
`guna-milan-tables.ts`): группы вашьи взяты по символу знака целиком, без половинных
границ Стрельца/Козерога, которые в классических текстах расходятся; таблица вражды
йони-животных — только хорошо задокументированные пары, не полная матрица 14×14.
**Требует сверки с практикующим астрологом перед выходом из беты** — тот же принцип,
что у аянамши Лахири (§6.1).

Гана-кута асимметрична по традиции, когда пол обоих людей известен (роль
жениха/невесты в классической таблице), и берёт более благоприятное направление,
когда пол неизвестен или пара однополая — `union` поддерживает `format: any` и не
требует указывать пол.

### 16.3 ИИ-разбор переиспользует существующую инфраструктуру

`AstroGenerationService.generateCompatibility` — второй метод поверх того же
HTTP-клиента, что и обычные разделы карты (`complete()` вынесен в общий приватный
метод при рефакторинге). В промпт уходит **только разбивка по восьми критериям**
— числа и короткие пояснения, без карт, дат, мест рождения и имён обеих сторон;
проверено тестом (`scoreArg` не содержит `bornAtUtc`/`latitude`).

Кэш — `AstroCompatibilityReading`, ключ `pairKey` (отсортированная пара отпечатков
карт) + язык + версия промпта. Сортировка убирает направление: неважно, кто из
двоих запросил разбор первым, текст один на пару. Квота и kill-switch — те же
`AstroQuotaService`/`AstroSettingsService`, что и у обычных разборов; при
выключенном ИИ очки гуна-милана остаются видны, пропадает только текст.

### 16.4 Точка входа из Union

`recommendation-card.tsx` — ссылка «Проверить совместимость по звёздам» на
`/astro/compatibility?with={userId}`. Это единственное касание Union: передаётся
голый id в URL, а не вызов сервиса — `astro` по-прежнему не импортирует
`UnionModule` и ничего не знает о статусе мэтча. Повторный переход по той же ссылке
не дублирует запрос: клиент сверяет уже загрученный список перед созданием.

`UsersModule` импортирован в `AstroModule` для `resolveAvatarUrl` — по тому же
прецеденту, что уже применён в `UnionModule` (см. `union-profile.service.ts`), а не
как новое исключение из контракта изоляции.

### 16.5 Проверено вживую

Полный цикл прогнан через реальный API и браузер, не только юнит-тестами: заявка от
одного демо-аккаунта другому, просмотр как «входящая» у получателя, принятие,
идентичный счёт `23.5 из 36` на обеих сторонах после принятия, деградация ИИ-текста
без потери очков при отсутствии `ASTRO_AI_API_KEY`, отказ в доступе третьему
аккаунту (403), отсутствие дублирования запроса при повторном переходе по ссылке
из Union (подтверждено по сетевым запросам — только GET, без лишнего POST).
