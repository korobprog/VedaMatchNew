# Российский контур — план реализации

> **Для агентов:** ОБЯЗАТЕЛЬНЫЙ СУБ-СКИЛЛ: используйте
> superpowers:subagent-driven-development (рекомендуется) или
> superpowers:executing-plans, чтобы выполнять план по задачам. Шаги помечены
> чекбоксами (`- [ ]`).

**Цель:** персональные данные россиян записываются сначала в московскую базу,
копия уезжает в амстердамскую. Признак резидентности проставляется при
регистрации и больше не теряется.

**Устройство:** у `User` появляется `dataResidency`. Появляется второй клиент
Prisma на московскую базу с узкой схемой — только то, что идентифицирует
человека. Все записи персональных данных идут через один модуль: для `ru` —
Москва, дождаться подтверждения, затем Амстердам; для `global` — только
Амстердам. Чтения не меняются, идут из Амстердама.

**Стек:** NestJS, два клиента Prisma 6.16, Jest (`*.spec.ts` рядом с кодом),
Postgres в Амстердаме и Timeweb в Москве.

**Спецификация:**
[2026-09-03-auth-providers-and-ru-residency-design.md](../specs/2026-09-03-auth-providers-and-ru-residency-design.md),
разделы «Российский контур» и «User.dataResidency». Первый этап —
[2026-09-03-identities-and-yandex-id.md](2026-09-03-identities-and-yandex-id.md),
выполнен и выкачен.

## Правило простановки признака изменилось 2026-09-04

По итогам правового разбора: **способ входа не устанавливает гражданство**, а
значит выводить из него резидентность нельзя. Действует другое правило —
**неизвестно, значит Россия**. Гражданства мы не спрашиваем ни у кого, поэтому
на практике `ru` у всех; 108 прежних аккаунтов переведены миграцией
`20260904100000_residency_defaults_to_ru`.

Три следствия для этого плана:

1. **Вопрос «куда писать первую запись при входе по почте» снят.** Адрес, код и
   IP пишутся сразу в российскую базу для всех, гражданство выяснять не нужно.
   Второй план от этого становится проще, а не сложнее.
2. **Московская база стала несущей.** Пока `ru` был у одного человека из 109,
   её недоступность ломала регистрацию единицам. Теперь — любую регистрацию и
   любую правку профиля. Гасить её нельзя; задача 7 (фоновая досылка) и
   требования к доступности из необязательных становятся обязательными.
3. **Фотографии — единственный неразобранный пункт.** Предварительный ответ
   говорит «не биометрия, перенос хранилища не требуется» и тут же
   «локализовать как обычные ПД нужно». Эти два утверждения не сходятся:
   если изображение подлежит локализации, оно должно лежать в РФ, а это и есть
   перенос. До разъяснения хранилище не трогаем.

## Про VK и вход по почте

Их как способов входа ещё нет — это второй план. Но **отдельной работы по
контуру они не потребуют:** маршрутизация идёт по `dataResidency`, а не по
провайдеру. Как только способ появится и проставит `ru`, данные поедут в Москву
сами. Поэтому контур делается один раз, здесь.

Единственное, что нужно от второго плана: у входа по почте признак берётся из
домена регистрации, и **записать его надо в момент создания пользователя** —
задним числом он не восстановим (см. спецификацию, «Когда заводить поле»).

## Общие ограничения

- `uuid` пользователя генерирует приложение, а не база: оба хранилища должны
  получить одинаковый `User.id`. В `IdentityService` это уже так.
- Порядок записи для `ru` — Москва первой. Именно порядок делает схему
  законной, менять его нельзя ни ради скорости, ни ради простоты.
- Чтения не переносить. Каждое чтение через полконтинента — лишние сто
  миллисекунд на страницу.
- Обращений к московскому клиенту из сервисных модулей быть не должно: только
  через модуль записи. Это то же правило, что и контракт сервисного модуля.
- Перечень персональных полей — **один список в коде**. Состав спецификация
  называет открытым вопросом к юристу, и ответ должен быть правкой в одном
  месте.
- Новая переменная окружения дописывается в три места: `.env.example`,
  `environment` сервиса `api` в `portal/docker-compose.dokploy.yml`, панель
  Dokploy. Пропуск второго не ловится ни тестами, ни типами.
- Тесты: `pnpm --filter @vedamatch/api test`.
- Секреты только из переменных окружения. Репозиторий публичный.

- [ ] **Шаг 3: поле в схеме**

Рядом с портальными энумами:

```prisma
// Где хранятся персональные данные человека. Определяется способом
// регистрации и не меняется: VK ID и Яндекс ID — российские информационные
// системы, Google — нет, у входа по почте признак берётся из домена.
enum DataResidency {
  ru
  global
}
```

В `User`, рядом с `role`:

```prisma
  dataResidency                DataResidency
```

Без `?` и без `@default`: обязательное поле заставляет каждую точку создания
пользователя ответить на вопрос осознанно, а не унаследовать `global` молча.

- [ ] **Шаг 4: миграция с бэкфиллом в три такта**

Колонка добавляется необязательной, заполняется, затем становится
обязательной — иначе миграция упадёт на 109 существующих строках.

```sql
CREATE TYPE "DataResidency" AS ENUM ('ru', 'global');

ALTER TABLE "User" ADD COLUMN "dataResidency" "DataResidency";

-- Признак берётся у САМОЙ РАННЕЙ идентичности: после привязки второго способа
-- у человека будет и google, и yandex, и выбор «любой» разложил бы признак
-- случайно.
UPDATE "User" u
SET "dataResidency" = CASE
  WHEN first.provider IN ('yandex', 'vk') THEN 'ru'::"DataResidency"
  ELSE 'global'::"DataResidency"
END
FROM (
  SELECT DISTINCT ON ("userId") "userId", provider
  FROM "UserIdentity"
  ORDER BY "userId", "createdAt" ASC, id ASC
) AS first
WHERE first."userId" = u.id;

-- Аккаунты без идентичностей (дев-вход по паролю, демо-сид) — global.
UPDATE "User" SET "dataResidency" = 'global' WHERE "dataResidency" IS NULL;

ALTER TABLE "User" ALTER COLUMN "dataResidency" SET NOT NULL;
```

`apps/api/prisma/ru/schema.prisma`. Отдельный `generator` с собственным

```prisma
generator client {

  provider = "postgresql"

// Только то, что идентифицирует человека. Границу проводит спецификация:

model PersonalRecord {

  email         String    @unique
  name          String
  spiritualName String?
  birthDate     DateTime? @db.Date
  gender        String?
  avatarKey     String?
  photoKeys     String[]  @default([])
  createdAt     DateTime  @default(now())
  updatedAt     DateTime  @updatedAt

  birth PersonalBirthData?

  @@index([copiedAt])

model PersonalBirthData {
  recordId       String         @id

  longitude      Float
  timeZone       String
  updatedAt      DateTime       @updatedAt
```

### Задача 5: Точки записи переводятся на модуль

> **Состояние на 2026-09-04: готово.** Переведены все точки записи
> персональных данных: регистрация (`identity.service.ts`), правка профиля и

> (`account-anonymize.service.ts`) стирает и московскую запись.
>
> Сборка персональной записи живёт в одном месте — `PersonalDataService`.
> Точки передают только то, что меняют: `fields`, дельту ключей фотографий или
> данные рождения; остальное дочитывается из основной базы. Иначе перечень
