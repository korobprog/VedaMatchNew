# Перенос портала на домен vedamatch.com

Рабочий документ переезда с `vedamatch.ru` на `vedamatch.com` как основной
домен. `.ru` остаётся и отдаёт 301 на `.com` с сохранением пути и query.

Статус: **шаг 1 (разведка) — по коду выполнен, по серверу не выполнен.**
Ничего в проде не менялось.

## 0. Что не удалось проверить

С машины разработки нет исходящего доступа: `dig` не отвечает, `ssh
root@64.130.62.129` — `Permission denied (publickey,password)`. То же
записано в [HANDOFF.md](../HANDOFF.md) («с машины разработки нет исходящего
доступа… ssh на прод», проверено 29.08.2026). Поэтому не проверены:
фактические DNS-записи обоих доменов, конфиг реверс-прокси на сервере,
процесс-менеджер, состояние сертификатов, боевые значения переменных.

Всё ниже — из репозитория. Серверную часть надо снять с самого сервера.

## 1. Расхождение с описанием задачи

В задаче сказано «nginx + certbot». В репозитории nginx и certbot нет вовсе:

- [Caddyfile](../Caddyfile) — Caddy с автоматическим TLS, блоки
  `vedamatch.ru` → `web:3000` и `api.vedamatch.ru` → `api:4000`
  (`request_body max_size 120MB` для галереи);
- [docker-compose.yml](../docker-compose.yml) — Caddy в профиле `prod`,
  порты 80/443, тома `caddy_data`/`caddy_config`;
- [portal/docker-compose.dokploy.yml](../portal/docker-compose.dokploy.yml) —
  боевой стек: внешняя сеть `dokploy-network`, сервисы только `expose`,
  наружу смотрит Traefik самого Dokploy; переменные задаются в панели
  Dokploy, не в файле.

Комментарий в [apps/api/src/main.ts:22](../apps/api/src/main.ts) («за Traefik,
единственный хоп на dokploy-network») подтверждает: на проде, скорее всего,
**Dokploy + Traefik**, а TLS выпускает Traefik через ACME, а не certbot.

Тогда шаг 3 выглядит иначе: не `nginx -t` и не certbot, а домены в
приложении Dokploy (Domains: host, порт контейнера, certificateProvider
letsencrypt) плюс отдельный роутер-редиректор для `.ru`. Требование
«копия конфига с суффиксом .bak» к панели Dokploy неприменимо — там
эквивалент это экспорт настроек приложения перед правкой.

**Нужно решение:** снять реальную конфигурацию с сервера и подтвердить, чем
терминируется TLS. Пока это не подтверждено, шаг 3 писать не по чему.

## 2. Что в коде завязано на домен

### Ломается при смене домена

| Место | Что | Риск |
| --- | --- | --- |
| `API_PUBLIC_URL` → [jwt.service.ts:35](../apps/api/src/modules/auth/jwt.service.ts) | issuer подписи и **проверки** access-JWT | смена значения делает все выданные access-токены невалидными |
| `COOKIE_DOMAIN` → [auth.service.ts:121](../apps/api/src/modules/auth/auth.service.ts) | домен `access_token`, `refresh_token`, маркера сессии | куки `.vedamatch.ru` физически не долетают до `.com` — все залогиненные разлогинятся, это неустранимо |
| `WEB_ORIGIN` → [main.ts:7](../apps/api/src/main.ts) | список CORS-origin (`credentials: true`) | без нового домена браузерные запросы к API падают |
| `NEXT_PUBLIC_API_URL` → [apps/web/Dockerfile:6](../apps/web/Dockerfile) | адрес API, **вшивается в бандл на сборке** (≈40 клиентских компонентов) | правка переменной без пересборки образа не действует |
| `AuthProviderSetting.domains` (миграция [20260903130000](../apps/api/prisma/migrations/20260903130000_auth_provider_settings/migration.sql), сверка в [auth-providers.service.ts](../apps/api/src/modules/auth/auth-providers.service.ts)) | список хостов портала: `['vedamatch.ru','localhost']` | на `vedamatch.com` список способов входа окажется пустым → войти нельзя вообще |
| redirect_uri OAuth: `${API_PUBLIC_URL}/auth/{google,yandex,vk}/callback` | сверяется провайдером | в Google/Яндекс/VK надо добавить новые URI **до** переключения |

`portalHost()` срезает префикс `api.`, то есть в `domains` нужен именно
`vedamatch.com` (и, если www тоже будет отдавать приложение, `www.vedamatch.com`
— но при 301 www→apex он не понадобится).

Refresh-токен — случайные 48 байт с хэшем в БД, к домену не привязан. То есть
сессия умирает не из-за токена, а из-за куки: браузер просто не отправит её на
другой регистрируемый домен. Разлогин всех — ожидаемое следствие переезда,
а не ошибка.

[geo.controller.ts:21,320](../apps/api/src/modules/users/geo.controller.ts) —

### Чего в проекте нет

`robots.txt` и `sitemap.xml` отсутствуют — ни статических файлов в
`apps/web/public`, ни `robots.ts`/`sitemap.ts` в `app/`. Пункт «обновить
sitemap и robots» превращается в «завести их», и это отдельная задача, не

нём нет, но после переезда гость на `.com` увидит лендинг — это и есть
ожидаемое поведение при сброшенных куках.

## 3. Пробел в плане DNS

В задаче перечислены только `A @` и `A www`. Приложению нужен третий
адрес: API живёт на отдельном хосте (`api.vedamatch.ru` сейчас). Без
`A api → 64.130.62.129` и сертификата на `api.vedamatch.com` портал на `.com`
поднимется, но ни один запрос к API не пройдёт.

Минимальный набор для Cloudflare (проксирование включено для web-записей):

| Тип | Имя | Значение | Proxy |
| --- | --- | --- | --- |
| A | `@` | 64.130.62.129 | вкл |
| A | `www` | 64.130.62.129 | вкл |
| A | `api` | 64.130.62.129 | вкл (см. оговорку) |

Оговорка по `api` под оранжевым облаком: у Cloudflare на бесплатном тарифе
потолок тела запроса 100 МБ, а Caddyfile разрешает 120 МБ и Музыка принимает
файлы до 150 МБ (`MUSIC_MAX_UPLOAD_BYTES=157286400`). Загрузка крупных
записей начнёт отдавать 413. Либо `api` серым облаком (DNS only), либо
принять ограничение осознанно.

Остальные записи (MX, SPF/DKIM/DMARC, TXT-верификации, SRV, AAAA) снимаются
с firstvds и переносятся один в один — с этой машины их не видно. Почтовые
записи всегда серым облаком.

## 4. Порядок работ, чтобы `.ru` не упал

1. Добавить в OAuth-провайдеры новые redirect_uri, старые не убирать.
2. `AuthProviderSetting.domains`: дописать `vedamatch.com` к существующим —
   массив, а не замена, тогда `.ru` продолжает работать.
3. Поднять на сервере домены `.com` **рядом** с `.ru`: оба хоста отдают
   приложение, сертификаты на оба. Проверить `.com` целиком.
4. Только после этого переключать переменные (`API_PUBLIC_URL`,
   `WEB_ORIGIN`, `COOKIE_DOMAIN`, `NEXT_PUBLIC_SITE_URL`, `WEB_PUBLIC_URL`,
   `NEXT_PUBLIC_API_URL`) и пересобирать образ web.
5. Последним шагом — 301 с `.ru` на `.com`.

`WEB_ORIGIN` на время перехода держать списком обоих доменов (код уже умеет
запятую), чтобы окно между пересборкой и редиректом никого не выбило.

## 5. Про 301 с .ru на .com

Аудитория портала русскоязычная. Зона `.ru` для неё привычнее, а `.com` под
российскими провайдерами исторически ходит хуже. Плюс постоянный редирект с
`.ru` отдаёт SEO-вес `.com` и обратно уже не отыгрывается. Это замечание, а
не возражение: решение за владельцем.

## 6. Регистратор: NiceNIC, но после NS

Решение владельца: `vedamatch.com` уезжает с Timeweb на NiceNIC, код переноса
уже на руках. На переезд сайта это не влияет — смена регистратора не трогает
ни NS, ни записи в зоне, домен всё это время продолжает резолвиться туда же.

Порядок остаётся «NS вперёд». Смена NS **не накладывает** запрет на перенос:
60-дневный лок по политике ICANN даёт смена регистранта, а не делегирования.
Значит NS можно переключить сегодня и не платить за это ничем.

Обратный порядок стоит недели: пока перенос висит, домен трогать нельзя, и
переезд сайта встаёт в очередь за ним.

Последовательность:

1. Снять записи с firstvds (весь список, TXT в первую очередь).
2. Завести зону в Cloudflare, залить записи, **проверить ответы прямо у
   Cloudflare NS до переключения** — `dig @<ns>.ns.cloudflare.com vedamatch.com MX`.
3. Переключить NS в Timeweb. A-запись пока оставить старой (45.150.9.229) —
   ничего не меняется, проверяется только сам переезд зоны.
4. Дождаться делегирования: у зоны `com` TTL NS-записей 172800 (48 ч).
5. Дальше две независимые ветки: переезд сайта (шаги 3–5) и перенос
   регистратора на NiceNIC. Не одновременно.

Перед запуском переноса проверить:

- дата окончания регистрации не в ближайший месяц — перенос рядом с
  продлением рискован (перенос добавляет год, но не спасает от просрочки);
- адрес регистранта в WHOIS живой: туда придёт подтверждение;
- контакты в WHOIS **не менялись последние 60 дней** — иначе реестр откажет
  независимо от кода;
- у NiceNIC уточнить, сохраняет ли он NS при входящем переносе. Если NS уже
  на Cloudflare, худший случай — переставить их обратно в панели NiceNIC;
  зона при этом цела, потому что живёт не у регистратора.

Пока перенос в статусе pending — в домене не менять ничего.

## 7. Что видно в панели Timeweb (06.09.2026)

Снято с карточки домена владельцем:

- оплачен до **12 ноября 2026**, **автопродление выключено**;
- скрытие данных администратора выключено — контакты открыты в WHOIS;
- **«Управление NS-серверами недоступно»** — пункт неактивен, причина в
  подсказке не прочитана;
- «Передача домена» в панели означает передачу на другой аккаунт внутри
  Timeweb Cloud, а не трансфер к другому регистратору.

Почтовых ящиков на `vedamatch.com` нет (со слов владельца). Значит MX и
почтовые TXT переносить нечего — при снятии зоны это надо подтвердить
фактическими записями, но планировать миграцию почты не нужно.

### Следствие для порядка работ

Раздел 6 исходил из того, что NS переключаются в панели регистратора. Если
пункт действительно заблокирован и Timeweb не разблокирует его по обращению,
порядок переворачивается: **сначала трансфер на NiceNIC, NS — уже там.**

Простой при этом нулевой: `.com` и сегодня показывает старый сервер, а `.ru`
работает и в процессе не участвует. Пять дней ожидания ничего не ломают.
Трансфер заодно закрывает вопрос продления — добавляет год к сроку.

Страховка на время трансфера: **включить автопродление**. Срок 12 ноября, и
если перенос сорвётся и о нём забудут, домен просто перестанет существовать.
Выключить обратно можно после переезда.

Скрытие WHOIS до конца трансфера не включать — подтверждение переноса идёт
на открытый адрес регистранта. Включить после.

## 8. Решение: трансфер первым, всё остальное в NiceNIC

Владелец решил: управление NS в Timeweb заблокировано, код трансфера на руках,
поэтому домен сначала переезжает к NiceNIC, а делегирование и записи
настраиваются уже там. Раздел 6 в части «NS вперёд» этим отменяется.

### До запуска трансфера: снять зону

Единственное, что обязано быть сделано заранее. Причина: неизвестно,
сохранит ли NiceNIC делегирование на `ns1/ns2.firstvds.ru` при входящем
переносе. Если подставит свои NS — зона окажется пустой, и домен погаснет,
пока записи не заведут заново. Восстанавливать их будет неоткуда: аккаунт
firstvds — чужая территория, которую вы покидаете.

Доступ в панель firstvds для этого не нужен. Почты на домене нет, а значит
нет и DKIM-селекторов — единственного типа записей, который снаружи не
перечисляется. Всё остальное спрашивается у авторитетного NS напрямую:

```bash
NS=ns1.firstvds.ru; D=vedamatch.com
for T in NS SOA A AAAA MX TXT CAA; do dig +noall +answer @$NS $D $T; done
for S in www api mail webmail ftp cdn static m dev staging old blog admin _dmarc; do
  for T in A CNAME TXT; do dig +noall +answer @$NS $S.$D $T; done
done
dig @$NS $D AXFR +noall +answer   # обычно откажут, изредка отдают зону целиком
```

Вывод сохранить файлом — это и есть эталон, по которому зона восстанавливается
в Cloudflare. Отдельно посмотреть на `CAA`: запись, привязывающая выпуск
сертификатов к конкретному удостоверяющему центру, тихо запретит Let's Encrypt
на новом сервере, и ошибка будет выглядеть как необъяснимый отказ ACME.

### Порядок

1. Снять зону (выше), сохранить файл.
2. `whois vedamatch.com` — убедиться, что нет `clientTransferProhibited`.
3. Запустить трансфер в NiceNIC, подтвердить письмом на адрес регистранта.
4. Пока статус pending — **не трогать в домене ничего**, ни там, ни в Timeweb.
5. После завершения: в NiceNIC поставить NS Cloudflare, в Cloudflare залить
   зону из снимка плюс `A @`, `A www`, `A api` → 64.130.62.129.
6. Дальше — переезд сайта, разделы 2–4.

Трансфер добавляет год к сроку регистрации, то есть заодно закрывает
12 ноября 2026. Но пока он не завершён, срок прежний: если перенос сорвётся
и о нём забудут — домен погибнет. Автопродление в Timeweb на это время стоит
включить.

## 9. Пошаговая инструкция

### Шаг A. Сегодня, до запуска трансфера (10 минут)

**A1. Снять зону** — команды в разделе 8. Вывод сохранить файлом.

**A2. Проверить, снят ли замок:**

```bash
whois vedamatch.com | grep -iE "status|expir|registrar"
```

`clientTransferProhibited` в статусах — трансфер отклонят даже с верным
кодом; сначала снять замок через поддержку Timeweb.

**A3. Включить автопродление в Timeweb.** Оплачено до 12.11.2026,
автопродление выключено. Трансфер добавит год, но только когда завершится.

### Шаг B. Запуск трансфера

**B1.** В NiceNIC оформить перенос `vedamatch.com`, ввести код.

**B2.** Подтвердить письмо от NiceNIC на адрес регистранта (проверить спам).
Отсчёт начинается только после этого клика.

**B3.** Написать в поддержку Timeweb: «подтвердите передачу домена другому
регистратору». У теряющего регистратора по политике ICANN 5 календарных дней
на ответ; при явном согласии перенос закрывается за минуты вместо пяти суток.

**B4.** Пока статус pending — в домене не менять ничего.

### Шаг C. Параллельно, пока идёт трансфер

От DNS не зависит, делается сразу.

**C1. Redirect URI в OAuth.** Добавить, старые не удалять:

- Google Cloud Console → Credentials → OAuth client → Authorized redirect URIs:
  `https://api.vedamatch.com/auth/google/callback`
- Яндекс/VK — аналогично `/auth/yandex/callback`, `/auth/vk/callback`,
  если способы включены.

**C2. Добавить домен в `AuthProviderSetting.domains`.** Админки для этого
поля нет — только SQL в боевой базе. Запрос идемпотентный и дописывает
элемент, не заменяя массив, поэтому `.ru` продолжает работать:

```sql
SELECT "provider", "enabled", "domains" FROM "AuthProviderSetting";

UPDATE "AuthProviderSetting"
   SET "domains" = array_append("domains", 'vedamatch.com'),
       "updatedAt" = now()
 WHERE 'vedamatch.ru' = ANY("domains")
   AND NOT ('vedamatch.com' = ANY("domains"));

SELECT "provider", "enabled", "domains" FROM "AuthProviderSetting";
```

Без этого на новом домене список способов входа окажется пустым и войти
будет нельзя вообще.

**C3. Завести зону в Cloudflare** (free, режим DNS only) и залить записи из
снимка. NS не переключать — зона просто лежит и ни на что не влияет.

**C4. Снять конфигурацию сервера.** Единственное белое пятно: репозиторий
говорит Dokploy + Traefik, постановка задачи говорила nginx + certbot.
Только чтение, ничего не меняет:

```bash
ss -tlnp | grep -E ':(80|443)'          # кто на самом деле держит 80/443
docker ps --format '{{.Names}}\t{{.Image}}'
docker network ls | grep -i dokploy
systemctl status nginx --no-pager 2>&1 | head -5
ls /etc/nginx/sites-enabled/ 2>/dev/null
certbot certificates 2>/dev/null | head -20
ls /etc/letsencrypt/live/ 2>/dev/null
```

### Шаг D. После завершения трансфера

**D1.** В NiceNIC поставить NS Cloudflare (два адреса из панели Cloudflare).

**D2.** Дождаться делегирования, проверить: `dig +short vedamatch.com NS`.

**D3.** В Cloudflare поставить `A @`, `A www`, `A api` → 64.130.62.129,
TTL низкий, режим DNS only.

Короткий провал на `.com` в этот момент допустим: домен и так показывает
устаревшую версию на старом сервере, и от него ничего не зависит. `.ru` не
затрагивается.

**D4.** На сервере добавить `vedamatch.com`, `www.vedamatch.com`,
`api.vedamatch.com` и выпустить сертификаты. Точные действия — после C4.

**D5.** Проверить `.com` целиком: страницы, API, вход.

### Шаг E. Переключение

**E1.** Переменные окружения: `API_PUBLIC_URL`, `WEB_ORIGIN` (оба домена
через запятую на время перехода), `COOKIE_DOMAIN`, `NEXT_PUBLIC_SITE_URL`,
`WEB_PUBLIC_URL`, `NEXT_PUBLIC_API_URL`.

**E2. Пересобрать образ web.** `NEXT_PUBLIC_API_URL` вшивается на сборке —
рестарта недостаточно.

**E3.** Проверить вход и регистрацию. Все залогиненные разлогинятся: куки
`.vedamatch.ru` на `.com` не долетают. Это неустранимо и ожидаемо.

**E4.** 301 с `.ru` и `www.ru` на `https://vedamatch.com$request_uri` —
последним шагом, когда `.com` уже проверен.

**E5.** Включить скрытие данных WHOIS в NiceNIC. До конца трансфера не
включать: подтверждение идёт на открытый адрес регистранта.

### Контрольные точки

После A, C и D — короткий отчёт, дальше не идти без сверки.

## 10. Что уже сделано в репозитории (коммит 7690b41)

Всё, что можно было подготовить без DNS и без доступа на сервер. Ни одна из
правок не меняет поведение работающего `.ru` до явной установки переменных.

- **Caddyfile** отдаёт приложение на `vedamatch.com` и `vedamatch.ru` сразу,
  `api.` — на обоих, `www.vedamatch.com` уводит на апекс. 301 с `.ru` не
  добавлен намеренно: это шаг E4.
- **Миграция** `20260906120000_auth_providers_com_domain` дописывает
  `vedamatch.com` в `AuthProviderSetting.domains`. Шаг C2 инструкции больше
  не нужен — накатится сама при деплое (`docker-entrypoint.sh` вызывает
  `prisma migrate deploy`). Руками ничего выполнять не надо.
- **`WEB_PUBLIC_URL` и `NEXT_PUBLIC_SITE_URL` теперь пробрасываются.**
  Находка на ровном месте: ни один compose их не передавал, и в бою работали
  зашитые в код дефолты `https://vedamatch.ru`. То есть на шаге E задать их
  в панели Dokploy было бы недостаточно — значение просто не дошло бы до
  процесса. `NEXT_PUBLIC_SITE_URL` вдобавок стал build-arg'ом: префикс
  `NEXT_PUBLIC_` вшивается на сборке.

Осталось за пределами репозитория: панели регистраторов, Cloudflare,
OAuth-консоли, всё на сервере. С этой машины нет ни DNS, ни ssh.

## 11. Снимок зоны vedamatch.com (06.09.2026)

Снято с `ns1.firstvds.ru`. Всё, что вернул авторитетный сервер:

```
vedamatch.com.      3600 IN NS    ns1.firstvds.ru.
vedamatch.com.      3600 IN NS    ns2.firstvds.ru.
vedamatch.com.      3600 IN SOA   ns1.firstvds.ru. korobprog.gmail.com. 2025122700 ...
vedamatch.com.      3600 IN A     45.150.9.229
vedamatch.com.      3600 IN MX    10 mail.vedamatch.com.
vedamatch.com.      3600 IN MX    20 mail.vedamatch.com.
www / api / mail / webmail / ftp / cdn / static / m / dev / staging / old /
blog / admin / _dmarc   →  A 45.150.9.229
```

Нет `AAAA`, нет `TXT` (ни одной — ни SPF, ни верификаций), нет `CAA`.

### Три вывода

**1. MX существуют, хотя почта считалась отсутствующей.** Два приоритета на
`mail.vedamatch.com`, который смотрит на старый сервер. При этом ни SPF, ни
DKIM, ни DMARC в зоне нет — с такой конфигурацией исходящая почта всё равно
попадала бы в спам. Похоже на шаблон панели хостинга (ISPmanager на FirstVDS
заводит `mail`, `webmail`, `ftp` и MX сам), а не на живой почтовый узел. Но
подтвердить это должен владелец: если хоть один адрес `@vedamatch.com`
где-то указан контактом, отказ от MX убивает переписку молча.

**2. В зоне почти наверняка wildcard `*`.** Признак: на `_dmarc` вернулась
`A`-запись. Никто не заводит `A` для `_dmarc` — там по назначению бывает
только `TXT`. То есть отвечает не тринадцать настроенных поддоменов, а одна
звёздочка. Проверяется одним запросом на заведомо несуществующее имя.

Переносить wildcard в новую зону не стоит: он маскирует опечатки и заставляет
любой несуществующий поддомен отвечать рабочим адресом. Лучше три явных
записи.

**3. Хорошие новости.** `CAA` нет — выпуск Let's Encrypt ничем не ограничен.
`TXT` нет — ни верификаций сервисов, ни SPF переносить не нужно. `AAAA` нет —
IPv6 не задействован.

### Набор записей для Cloudflare

Режим DNS only (серое облако) для всего: проксирование добавляет хоп и режет
тело запроса до 100 МБ на бесплатном тарифе, а Музыка принимает файлы до 150.

| Тип | Имя | Значение |
| --- | --- | --- |
| A | `@` | 64.130.62.129 |
| A | `www` | 64.130.62.129 |
| A | `api` | 64.130.62.129 |

И всё. Остальное из старой зоны — либо wildcard, либо шлейф почтового
шаблона; переносится только по решению владельца:

| Тип | Имя | Значение | Когда переносить |
| --- | --- | --- | --- |
| MX | `@` | 10/20 `mail.vedamatch.com` | только если почта реально нужна |
| A | `mail` | адрес почтового сервера | вместе с MX |
| A | `webmail` | адрес почтового сервера | вместе с MX |

Записи `ftp`, `cdn`, `static`, `m`, `dev`, `staging`, `old`, `blog`, `admin`
не переносятся: они не настроены, а отвечают из-за звёздочки.

## 12. WHOIS: настоящий регистратор — PDR, а не Timeweb

```
Registrar: PDR Ltd. d/b/a PublicDomainRegistry.com
Registrar IANA ID: 303
Domain Status: ok https://icann.org/epp#ok
Registry Expiry Date: 2026-11-12T07:45:05Z
```

**Timeweb — реселлер, а не регистратор.** Это и объясняет «Управление
NS-серверами недоступно» в его панели: делегированием распоряжается PDR, а
реселлер этой возможности наружу не даёт. Заодно снимает вопрос, стоит ли
пытаться разблокировать пункт — не стоит, после переезда к NiceNIC он
перестанет существовать.

**`Domain Status: ok` — замка нет.** Ни `clientTransferProhibited`, ни любого
другого запрета. Домен переносится прямо сейчас.

Практическое следствие: теряющая сторона в трансфере — PDR, и подтверждение
идёт через её механику. Обращение в поддержку Timeweb по-прежнему имеет
смысл (реселлер инициирует релиз у регистратора), но ждать письма и статусов
надо от PDR.

Подтверждение переноса придёт на адрес регистранта. В SOA зоны стоит
`korobprog.gmail.com`, то есть вероятнее всего туда же.

### Wildcard подтверждён

```
zzz-proverka-wildcard.vedamatch.com. 3600 IN A 45.150.9.229
```

Заведомо несуществующее имя отвечает рабочим адресом. Значит в зоне `*`, и
тринадцать «поддоменов» из раздела 11 — фикция. В новую зону не переносится.
