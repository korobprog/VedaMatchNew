# Перенос портала на домен vedamatch.com

Рабочий документ переезда с `vedamatch.ru` на `vedamatch.com` как основной
домен. `.ru` остаётся и отдаёт 301 на `.com` с сохранением пути и query.

Статус: **шаг 1 (разведка) — по коду выполнен, по серверу не выполнен.**
Ничего в проде не менялось.

## 0. Что не удалось проверить

С машины разработки нет исходящего доступа: `dig` не отвечает, `ssh
root@64.130.62.129` — `Permission denied (publickey,password)`. То же
записано в [HANDOFF.md](../HANDOFF.md) («с машины разработки нет исходящего
доступа… ssh на прод», проверено 29.08.2026). Поэтому не проверены:
фактические DNS-записи обоих доменов, конфиг реверс-прокси на сервере,
процесс-менеджер, состояние сертификатов, боевые значения переменных.

Всё ниже — из репозитория. Серверную часть надо снять с самого сервера.

## 1. Расхождение с описанием задачи

В задаче сказано «nginx + certbot». В репозитории nginx и certbot нет вовсе:

- [Caddyfile](../Caddyfile) — Caddy с автоматическим TLS, блоки
  `vedamatch.ru` → `web:3000` и `api.vedamatch.ru` → `api:4000`
  (`request_body max_size 120MB` для галереи);
- [docker-compose.yml](../docker-compose.yml) — Caddy в профиле `prod`,
  порты 80/443, тома `caddy_data`/`caddy_config`;
- [portal/docker-compose.dokploy.yml](../portal/docker-compose.dokploy.yml) —
  боевой стек: внешняя сеть `dokploy-network`, сервисы только `expose`,
  наружу смотрит Traefik самого Dokploy; переменные задаются в панели
  Dokploy, не в файле.

Комментарий в [apps/api/src/main.ts:22](../apps/api/src/main.ts) («за Traefik,
единственный хоп на dokploy-network») подтверждает: на проде, скорее всего,
**Dokploy + Traefik**, а TLS выпускает Traefik через ACME, а не certbot.

Тогда шаг 3 выглядит иначе: не `nginx -t` и не certbot, а домены в
приложении Dokploy (Domains: host, порт контейнера, certificateProvider
letsencrypt) плюс отдельный роутер-редиректор для `.ru`. Требование
«копия конфига с суффиксом .bak» к панели Dokploy неприменимо — там
эквивалент это экспорт настроек приложения перед правкой.

**Нужно решение:** снять реальную конфигурацию с сервера и подтвердить, чем
терминируется TLS. Пока это не подтверждено, шаг 3 писать не по чему.

## 2. Что в коде завязано на домен

### Ломается при смене домена

| Место | Что | Риск |
| --- | --- | --- |
| `API_PUBLIC_URL` → [jwt.service.ts:35](../apps/api/src/modules/auth/jwt.service.ts) | issuer подписи и **проверки** access-JWT | смена значения делает все выданные access-токены невалидными |
| `COOKIE_DOMAIN` → [auth.service.ts:121](../apps/api/src/modules/auth/auth.service.ts) | домен `access_token`, `refresh_token`, маркера сессии | куки `.vedamatch.ru` физически не долетают до `.com` — все залогиненные разлогинятся, это неустранимо |
| `WEB_ORIGIN` → [main.ts:7](../apps/api/src/main.ts) | список CORS-origin (`credentials: true`) | без нового домена браузерные запросы к API падают |
| `NEXT_PUBLIC_API_URL` → [apps/web/Dockerfile:6](../apps/web/Dockerfile) | адрес API, **вшивается в бандл на сборке** (≈40 клиентских компонентов) | правка переменной без пересборки образа не действует |
| `AuthProviderSetting.domains` (миграция [20260903130000](../apps/api/prisma/migrations/20260903130000_auth_provider_settings/migration.sql), сверка в [auth-providers.service.ts](../apps/api/src/modules/auth/auth-providers.service.ts)) | список хостов портала: `['vedamatch.ru','localhost']` | на `vedamatch.com` список способов входа окажется пустым → войти нельзя вообще |
| redirect_uri OAuth: `${API_PUBLIC_URL}/auth/{google,yandex,vk}/callback` | сверяется провайдером | в Google/Яндекс/VK надо добавить новые URI **до** переключения |

`portalHost()` срезает префикс `api.`, то есть в `domains` нужен именно
`vedamatch.com` (и, если www тоже будет отдавать приложение, `www.vedamatch.com`
— но при 301 www→apex он не понадобится).

Refresh-токен — случайные 48 байт с хэшем в БД, к домену не привязан. То есть
сессия умирает не из-за токена, а из-за куки: браузер просто не отправит её на
другой регистрируемый домен. Разлогин всех — ожидаемое следствие переезда,
а не ошибка.

### Дефолты с `.ru`, которые перебиваются переменными

- [layout.tsx:41](../apps/web/src/app/layout.tsx) — `NEXT_PUBLIC_SITE_URL ?? "https://vedamatch.ru"` (metadataBase, og:url);
- [notices.controller.ts:131](../apps/api/src/modules/notices/notices.controller.ts) — `WEB_PUBLIC_URL ?? 'https://vedamatch.ru'` (ссылки в iCal);
- [.env.example:184](../.env.example) — `VAPID_SUBJECT=mailto:support@vedamatch.ru` (адрес для Push-сервисов; менять, только если почта переезжает).

Захардкоженно без переменной, менять не обязательно:
[geo.controller.ts:21,320](../apps/api/src/modules/users/geo.controller.ts) —
User-Agent и Referer для Nominatim (это вежливая подпись к чужому API,
не адрес сайта).

### Чего в проекте нет

`robots.txt` и `sitemap.xml` отсутствуют — ни статических файлов в
`apps/web/public`, ни `robots.ts`/`sitemap.ts` в `app/`. Пункт «обновить
sitemap и robots» превращается в «завести их», и это отдельная задача, не
часть переезда. [manifest.ts](../apps/web/src/app/manifest.ts) домена не
содержит (все URL относительные) — правки не требует.

`apps/web/src/proxy.ts` режет доступ по наличию куки `access_token`; домена в
нём нет, но после переезда гость на `.com` увидит лендинг — это и есть
ожидаемое поведение при сброшенных куках.

## 3. Пробел в плане DNS

В задаче перечислены только `A @` и `A www`. Приложению нужен третий
адрес: API живёт на отдельном хосте (`api.vedamatch.ru` сейчас). Без
`A api → 64.130.62.129` и сертификата на `api.vedamatch.com` портал на `.com`
поднимется, но ни один запрос к API не пройдёт.

Минимальный набор для Cloudflare (проксирование включено для web-записей):

| Тип | Имя | Значение | Proxy |
| --- | --- | --- | --- |
| A | `@` | 64.130.62.129 | вкл |
| A | `www` | 64.130.62.129 | вкл |
| A | `api` | 64.130.62.129 | вкл (см. оговорку) |

Оговорка по `api` под оранжевым облаком: у Cloudflare на бесплатном тарифе
потолок тела запроса 100 МБ, а Caddyfile разрешает 120 МБ и Музыка принимает
файлы до 150 МБ (`MUSIC_MAX_UPLOAD_BYTES=157286400`). Загрузка крупных
записей начнёт отдавать 413. Либо `api` серым облаком (DNS only), либо
принять ограничение осознанно.

Остальные записи (MX, SPF/DKIM/DMARC, TXT-верификации, SRV, AAAA) снимаются
с firstvds и переносятся один в один — с этой машины их не видно. Почтовые
записи всегда серым облаком.

## 4. Порядок работ, чтобы `.ru` не упал

1. Добавить в OAuth-провайдеры новые redirect_uri, старые не убирать.
2. `AuthProviderSetting.domains`: дописать `vedamatch.com` к существующим —
   массив, а не замена, тогда `.ru` продолжает работать.
3. Поднять на сервере домены `.com` **рядом** с `.ru`: оба хоста отдают
   приложение, сертификаты на оба. Проверить `.com` целиком.
4. Только после этого переключать переменные (`API_PUBLIC_URL`,
   `WEB_ORIGIN`, `COOKIE_DOMAIN`, `NEXT_PUBLIC_SITE_URL`, `WEB_PUBLIC_URL`,
   `NEXT_PUBLIC_API_URL`) и пересобирать образ web.
5. Последним шагом — 301 с `.ru` на `.com`.

`WEB_ORIGIN` на время перехода держать списком обоих доменов (код уже умеет
запятую), чтобы окно между пересборкой и редиректом никого не выбило.

## 5. Про 301 с .ru на .com

Аудитория портала русскоязычная. Зона `.ru` для неё привычнее, а `.com` под
российскими провайдерами исторически ходит хуже. Плюс постоянный редирект с
`.ru` отдаёт SEO-вес `.com` и обратно уже не отыгрывается. Это замечание, а
не возражение: решение за владельцем.

## 6. Регистратор: NiceNIC, но после NS

Решение владельца: `vedamatch.com` уезжает с Timeweb на NiceNIC, код переноса
уже на руках. На переезд сайта это не влияет — смена регистратора не трогает
ни NS, ни записи в зоне, домен всё это время продолжает резолвиться туда же.

Порядок остаётся «NS вперёд». Смена NS **не накладывает** запрет на перенос:
60-дневный лок по политике ICANN даёт смена регистранта, а не делегирования.
Значит NS можно переключить сегодня и не платить за это ничем.

Обратный порядок стоит недели: пока перенос висит, домен трогать нельзя, и
переезд сайта встаёт в очередь за ним.

Последовательность:

1. Снять записи с firstvds (весь список, TXT в первую очередь).
2. Завести зону в Cloudflare, залить записи, **проверить ответы прямо у
   Cloudflare NS до переключения** — `dig @<ns>.ns.cloudflare.com vedamatch.com MX`.
3. Переключить NS в Timeweb. A-запись пока оставить старой (45.150.9.229) —
   ничего не меняется, проверяется только сам переезд зоны.
4. Дождаться делегирования: у зоны `com` TTL NS-записей 172800 (48 ч).
5. Дальше две независимые ветки: переезд сайта (шаги 3–5) и перенос
   регистратора на NiceNIC. Не одновременно.

Перед запуском переноса проверить:

- дата окончания регистрации не в ближайший месяц — перенос рядом с
  продлением рискован (перенос добавляет год, но не спасает от просрочки);
- адрес регистранта в WHOIS живой: туда придёт подтверждение;
- контакты в WHOIS **не менялись последние 60 дней** — иначе реестр откажет
  независимо от кода;
- у NiceNIC уточнить, сохраняет ли он NS при входящем переносе. Если NS уже
  на Cloudflare, худший случай — переставить их обратно в панели NiceNIC;
  зона при этом цела, потому что живёт не у регистратора.

Пока перенос в статусе pending — в домене не менять ничего.
