# Звонки в «Общении»: варианты и план

Статус: этапы 0–3 сделаны, этап 4 (живые устройства) — руками. Обновлено 2026-09-09.

## Что хотим

Аудио- и видеозвонок один на один между участниками личного диалога прямо
из чата: кнопка в шапке беседы, входящий звонок всплывает в любом разделе
портала, в ленте диалога остаётся запись «Звонок, 12 мин» или «Пропущенный».
Групповые звонки — не в первой версии, но архитектура не должна их закрывать.

## Что уже есть и на что опираемся

- **Транспорт сервер → клиент.** `GET /chat/stream` — SSE, один поток на
  пользователя, веер через Redis pub/sub (`ChatEventsService`). Событие
  `ChatStreamEvent` — размеченное объединение в `packages/shared/src/chat.ts`;
  добавить типы `call.*` — штатное расширение, а не новый канал.
- **Транспорт клиент → сервер.** Обычные POST под `AuthGuard`. Для сигналинга
  WebRTC этого достаточно: offer/answer/ICE — десяток сообщений за первые
  две секунды, потом тишина.
- **Присутствие и пуши.** `ChatPresenceService` (TTL 25 с в Redis) и
  `NotificationEvent` → web-push (`push-sender.service.ts`, VAPID,
  `public/sw.js`). Входящий звонок при закрытой вкладке — это ещё один пуш
  с кнопками «Ответить / Отклонить», механика уже стоит.
- **Права.** `chat-access.ts` знает, кто в диалоге и кто кого заблокировал;
  звонок — тот же вопрос «можно ли этому человеку писать этому», ответ уже
  есть.
- **Контракт модуля.** Звонок зависит от беседы, участников и блокировок —
  всё это внутри `modules/chat/`. Отдельный сервис `calls/` не имел бы права
  прочитать `ChatMember`, поэтому звонки — подпапка `modules/chat/calls/`
  по образцу `people/`, маршруты `chat/calls/*`, модели с префиксом `Chat`.
- **Инфраструктура.** Один сервер в Амстердаме за Traefik (Dokploy), Redis
  есть. Заметная часть пользователей в России; исходящие соединения с сервера
  к ряду внешних API блокируются (см. память `blocked-egress`).

## Варианты

### A. WebRTC точка-точка, свой сигналинг, свой TURN (coturn)

Браузеры соединяются напрямую, медиа не идёт через наш сервер. Сервер только
сводит стороны: передаёт offer/answer/ICE через уже существующий SSE и POST,
ведёт запись о звонке, шлёт пуш. Когда прямое соединение невозможно
(симметричный NAT, мобильные сети — на практике 15–30 % пар), медиа
ретранслирует coturn — контейнер рядом с API.

- Плюсы: ноль внешних сервисов и ноль поминутной оплаты; данные не покидают
  нашу инфраструктуру; всё в рамках контракта модуля; сигналинг переиспользует
  существующий поток; e2e-шифрование DTLS-SRTP из коробки в 1:1.
- Минусы: только 1:1 (для группы >3 P2P разваливается по каналу); coturn
  надо поставить и открыть порты; WebRTC-квирки iOS Safari лечим сами.
- Стоимость: трафик релея. Аудио ≈ 50 кбит/с, видео 1–2 Мбит/с в каждую
  сторону, и только для тех звонков, что пошли через TURN.

### B. Управляемый видеосервис (LiveKit Cloud, Daily, Twilio Video)

SDK в браузере, наш API выдаёт токен комнаты. Группы и запись — из коробки.

- Плюсы: быстрее всего до первого звонка; групповые звонки сразу.
- Минусы: поминутная оплата навсегда; медиа и метаданные уходят третьей
  стороне; клиенты из России до этих доменов дотягиваются нестабильно, а
  наш сервер до их API — тоже (та же история, что с Telegram Bot API);
  провайдер может закрыть аккаунт или регион. Зависимость, которую потом
  не убрать без переписывания клиента.

### C. Свой SFU (LiveKit self-hosted, mediasoup, Jitsi Videobridge)

Медиасервер у нас, клиент говорит с ним, а не с собеседником.

- Плюсы: группы, запись, адаптивные раскладки; не зависит от чужих панелей.
- Минусы: отдельный сервис с UDP-диапазоном, своим масштабированием и
  мониторингом; весь медиатрафик всех звонков идёт через сервер (для 1:1 это
  чистый перерасход); неделя-две одной только эксплуатации до первого
  звонка. Это верный ответ на вопрос «групповые звонки», но не на вопрос
  «позвонить собеседнику».

### D. Встроить Jitsi Meet (iframe на meet.jit.si или свой)

- Плюсы: день работы.
- Минусы: чужой интерфейс внутри нашего, нет входящего звонка в чате, нет
  записи в ленте, нет контроля над блокировками и модерацией, публичный
  инстанс не даёт гарантий. Годится как временная затычка, не как сервис.

## Почему A

1. **Продуктовая задача — 1:1.** Диалог в «Общении» двусторонний, и звонок
   из него — двусторонний. Для двух участников P2P даёт наименьшую задержку
   и не грузит сервер; SFU (C) здесь платит за возможность, которой не
   пользуется.
2. **Самая короткая новая поверхность.** Сигналинг — расширение уже
   работающего SSE и десяток POST-маршрутов. Новая инфраструктура — один
   контейнер coturn. В B и C новых подсистем больше, и они чужие.
3. **Не ставит продукт в зависимость от внешней доступности.** Опыт с
   заблокированным egress уже есть; звонки, которые перестают работать при
   очередной блокировке чужого домена, хуже отсутствия звонков.
4. **Совместим с контрактом без исключений.** Всё внутри `modules/chat/`,
   наружу — доменные события, никаких новых импортов.
5. **Не закрывает дорогу к группам.** Модель `ChatCall`, состояния,
   интерфейс звонка, входящий баннер, запись в ленте — общие. Когда
   понадобятся группы, под тем же UI меняется только «как течёт медиа»:
   вместо `RTCPeerConnection` к собеседнику — подключение к своему LiveKit
   (вариант C), который к тому моменту оправдан.

Главный риск A — сеть, и он же риск всех вариантов: в России периодически
душат UDP к зарубежным хостам, а сервер в Амстердаме. Поэтому coturn
обязан слушать и TCP/TLS на 443 (turns:), а первый этап плана — измерение,
а не код.

## Устройство

### Данные

```prisma
enum ChatCallKind   { audio video }
enum ChatCallStatus { ringing accepted declined missed ended failed cancelled }

model ChatCall {
  id             String         @id @default(cuid())
  conversationId String
  callerId       String
  calleeId       String
  kind           ChatCallKind
  status         ChatCallStatus @default(ringing)
  createdAt      DateTime       @default(now())
  answeredAt     DateTime?
  endedAt        DateTime?
  /// Сторона, завершившая звонок, и причина: hangup | timeout | network | busy.
  endedById      String?
  endReason      String?
  /// Пошёл ли звук через TURN — единственная метрика, ради которой стоит
  /// хранить строку, а не только сообщение в ленте.
  relayed        Boolean?
  @@index([conversationId, createdAt])
  @@index([callerId, createdAt])
  @@index([calleeId, createdAt])
}
```

Сигналинг (offer/answer/ICE) в базу не пишется: живёт в событиях, время жизни
— секунды. Активный звонок держится в Redis: `chat:call:user:<id>` → callId с
TTL, чтобы не принять второй входящий во время первого и чтобы «занято»
работало на нескольких инстансах.

В ленту диалога ложится обычное `ChatMessage` с вложением
`ChatAttachmentKind.call` (по образцу `notice`, `listing`): «Исходящий
аудиозвонок · 12:34», «Пропущенный видеозвонок». Так история звонков
видна там, где человек её ищет, и переживает удаление строки `ChatCall`.

### API (`modules/chat/calls/`)

| Маршрут | Что делает |
|---|---|
| `POST /chat/calls` `{conversationId, kind}` | Проверяет `denyWrite`, блокировку, что диалог личный, что оба не заняты. Создаёт `ChatCall`, шлёт `call.ringing` обоим, пуш `chat.call-incoming` вызываемому, ставит таймер 45 с → `missed`. |
| `POST /chat/calls/:id/accept` | Только вызываемый, только из `ringing`. `call.accepted` обоим — с этого момента стороны обмениваются SDP. |
| `POST /chat/calls/:id/decline` | `declined`, событие обоим, остальные вкладки вызываемого гасят баннер. |
| `POST /chat/calls/:id/signal` `{payload}` | Ретранслирует offer/answer/ICE второй стороне событием `call.signal`. Сервер содержимое не разбирает. |
| `POST /chat/calls/:id/end` `{reason, relayed?}` | `ended`/`cancelled`, считает длительность, пишет сообщение в ленту. |
| `GET /chat/calls/ice-servers` | STUN + TURN с короткоживущими HMAC-учётками coturn (`static-auth-secret`, TTL 10 мин). Постоянный пароль TURN наружу не отдаётся. |

Новые события в `ChatStreamEvent`: `call.ringing`, `call.accepted`,
`call.declined`, `call.signal`, `call.ended`. Наружу через
`EventEmitter2` — `chat.call.missed` для уведомлений («Вы пропустили звонок
от …»), самодостаточное, с именем звонившего внутри.

Чистая логика в отдельных модулях с тестами: `call-state.ts` (допустимые
переходы статусов и кто их вправе делать), `call-summary.ts` (текст записи в
ленте и длительность), `turn-credentials.ts` (HMAC-учётки).

### Веб

- **Один поток на вкладку, а не на экран.** Сейчас `subscribeToChat` вызывают
  `chat-list-view` и `chat-room`; входящий звонок должен доходить в любом
  разделе портала. Поток поднимается один раз в `(portal)/layout` через
  контекст, а список и комната подписываются на него, а не открывают свой.
- `lib/chat-calls-api.ts` — клиент маршрутов выше.
- `components/chat/calls/call-machine.ts` — чистая машина состояний звонка
  (idle → outgoing/incoming → connecting → active → ended) с тестами, без
  WebRTC внутри. `use-call.ts` — хук, который скармливает ей события SSE и
  `RTCPeerConnection`.
- `chat-call-overlay.tsx` — полноэкранный экран звонка: видео собеседника,
  своё превью, микрофон/камера/завершить, индикатор «через ретранслятор» и
  качество. `chat-incoming-call.tsx` — баннер входящего на любом экране,
  рингтон только после первого жеста пользователя (политика автовоспроизведения).
- Кнопки «Позвонить» и «Видео» в шапке `chat-room.tsx` — только для `direct`
  и только когда `denyWrite` пуст.
- `sw.js`: пуш `chat.call-incoming` с действиями «Ответить / Отклонить»;
  «Ответить» открывает `/chat/<conversationId>?call=<id>`.
- Реконнект: `iceRestart` при `disconnected` дольше 3 с, завершение при
  `failed` дольше 15 с; при обрыве SSE машина не роняет звонок — медиа
  идёт мимо сервера.
- Доступ к камере/микрофону запрашивается по нажатию, отказ объясняется
  словами, а не тишиной.

### Инфраструктура

- Контейнер `coturn/coturn` на том же сервере, `network_mode: host` (иначе
  диапазон UDP-портов через docker-proxy не проживёт): 3478 udp/tcp, 5349
  tls, relay-диапазон 49160–49400 udp. Сертификат тот же, что у домена
  (`turn.vedamatch.ru`). Помнить про `DOCKER-USER` (память
  `docker-bypasses-ufw`): порты открывать явно, остальное закрыть.
- `static-auth-secret` в env API и coturn, `realm`, `no-multicast-peers`,
  `denied-peer-ip` на приватные диапазоны — чтобы TURN не стал прокси во
  внутреннюю сеть.
- Переменные API: `TURN_HOST`, `TURN_SECRET`, `CALLS_ENABLED`.

### Админка (обязательна по правилу «каждому сервису — раздел»)

В `admin/chat` вкладка «Звонки»: выключатель `CALLS_ENABLED` на лету, журнал
звонков (кто, кому, статус, длительность, `relayed`), доля relayed за сутки,
доля `failed`, проверка coturn (сервер сам делает allocation тестовыми
учётками и показывает результат). Жалобы на звонок идут через существующий
`ChatReport` с полем `callId`.

Находки, которые без подготовки стали бы сюрпризом на этапе 2:

- **`Permissions-Policy` в Caddyfile запрещал камеру и микрофон** всем,
  включая свои страницы: `camera=(), microphone=()`. Исправлено на `(self)`.
  Проверено на проде 2026-09-09: заголовки там отдаёт Traefik, и этого
  заголовка нет вовсе — камере ничто не мешает.
- **443/tcp на сервере занят Traefik'ом**, поэтому `turns:` по умолчанию на
  5349, порт настраивается через `TURN_TLS_PORT`. Нужен ли 443 (и второй
  IP под него) — покажут измерения из российских сетей.
- **Боевой хост за 1:1 NAT** (внутри 192.168.195.2, снаружи 64.130.62.129):
  coturn запускается с `--external-ip=внешний/внутренний`. Проброс
  UDP-диапазона через NAT провайдера подтвердит только зонд.
- **Сертификат для `turn.vedamatch.ru` выпускает Traefik** через фиктивный
  маршрут, PEM для coturn достаёт `deploy/coturn/extract-cert.py` из
  `acme.json` по крону. Установка на хосте — руками по README: правки ufw,
  cron и Traefik на проде агент не делает.

## Известные ограничения

- Таймер дозвона живёт в процессе, принявшем звонок; при нескольких
  инстансах API застрявший `ringing` добивается при следующем обращении к
  звонку, а не ровно через 45 с.
- Перезагрузка вкладки посреди разговора: вызываемый поднимает медиа и ждёт
  новый offer, звонивший делает перезапуск ICE; если обе стороны перезагрузились
  разом — звонок завершится по таймеру обрыва как `failed`.
